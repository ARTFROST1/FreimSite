# CMS-BUILDING.md — как строить сайты в этом шаблоне под нашу CMS

> Аудитория этого файла — агент (или разработчик), который никогда не видел
> проект и должен добавить новый редактируемый блок или новую страницу так,
> чтобы клиент мог редактировать его через клиентский CMS-портал, ничего не
> сломав. Прочитай этот файл целиком **до** первой правки — конвенция
> неочевидна и расходится с «обычным» Astro-стартером.

**Этот файл — владелец темы «механика CMS».** Всё про то, КАК завести
редактируемый блок, живёт здесь и только здесь; другие документы ссылаются
сюда, а не пересказывают.

Смежное: [`CONTENT.md`](CONTENT.md) — политика («ЧТО вообще является
контентом», что нельзя отдавать клиенту); [`AGENT-PLAYBOOK.md`](AGENT-PLAYBOOK.md) —
процесс сборки сайта целиком, эта цепочка там один из этапов.
Этот файл — единственный, который обязателен целиком.

## Зачем это всё и как всё связано

Клиент правит сайт через внешний портал в двух режимах:

1. **Формы** — портал читает `content.schema.json` (контракт, сгенерированный
   из Zod-схем), рисует формы по нему и пишет обратно JSON-файлы в
   `src/content/`.
2. **Клик по превью** («TinaCMS-style» визуальный редактор) — портал
   открывает сайт в iframe с `?fd_edit=1`, `public/fd-edit.js` подсвечивает
   каждый элемент с атрибутом `data-cms="..."`, клик выделяет соответствующее
   поле в форме портала, а правка в форме тут же переписывает `textContent`
   этого элемента на странице (без перезагрузки).

Оба режима читают **один и тот же** источник правды — JSON в
`src/content/`. Zod-схема в `src/config/schemas.ts` — это единственное место,
откуда берутся (а) валидация на сборке, (б) TS-типы для компонентов, (в)
форма портала (через `.describe()`), (г) карта `data-cms`-атрибутов.

Полная цепочка, которой нужно следовать **неукоснительно** для любого нового
блока или страницы:

```
1. Zod-схема (src/config/schemas.ts, RU .describe() на каждом поле)
        │
2. JSON-контент (src/content/**/*.json — массив с id ИЛИ синглтон-объект)
        │
3. Коллекция (src/content.config.ts, defineCollection + file())
        │
4. Регистрация в контракте (scripts/generate-content-schema.ts → COLLECTIONS)
        │
5. Разметка в компоненте (data-cms="collection:itemId:field" на элементах)
        │
6. Рот-гвард (scripts/__tests__/annotations.test.ts — расширить карты полей)
        │
7. Регенерация + прогон (npx tsx scripts/generate-content-schema.ts; npm test)
```

Пропустишь шаг 4 — поле не появится в форме портала. Пропустишь шаг 5 —
поле правится только через форму, не по клику (не всегда плохо, но обычно
недоработка). Пропустишь шаг 6 — следующий разработчик молча снесёт
разметку рефакторингом, и никто не заметит до жалобы клиента.

## Шаг 1 — Zod-схема

Всё живёт в `src/config/schemas.ts`. Каждое поле, которое увидит редактор
на портале, **обязано** иметь `.describe('человеческая подпись на русском')`
— это единственный источник подписей формы, отдельного файла переводов нет.

Подпись поля портал строит как `description ?? <имя поля>`, поэтому поле без
`.describe()` показывает клиенту-нетехнарю **сырой английский ключ**
(`columns`, `heading`, `id`) посреди русского интерфейса. Замок —
`scripts/__tests__/generate-content-schema.test.ts` → «describes every field
in Russian»: он обходит весь сгенерированный контракт (`collections` +
`entries`, включая вложенные объекты и элементы массивов) и валит `npm test`
со списком неподписанных путей. Правило распространяется и на **объекты-
группы** (`footerSchema.columns`, `pagesSchema.about.heading`) — их
`description` становится заголовком группы полей в форме, — и на общий
`const id`.

```ts
export const featureSchema = z.object({
  id, // z.string().min(1) — см. ниже про id
  icon: z.string().describe('Иконка (SVG-путь 24×24 или один эмодзи)'),
  title: z.string().describe('Заголовок преимущества'),
  description: z.string().describe('Пояснение в одно-два предложения'),
});
export type Feature = z.infer<typeof featureSchema>;
```

Правила:

- **`id` — стабильный слаг, не для отображения.** Общий `const id = z.string().min(1)` уже объявлен в файле — переиспользуй его. Никогда не перенумеровывай существующие `id` при рефакторинге; добавляй новые. Смена `id` рвёт связь «эта карточка в CMS» ↔ «этот блок на сайте» и любые уже сохранённые правки.
- Вложенные объекты тоже получают `.describe()` — это подпись группы полей в форме (см. `sectionTextsSchema` — у каждого блока `.describe('Блок «Название»')`).
- Поле, которое **не должно** попасть клиенту (влияет на `href`, на JSON-LD, служебное) — просто не добавляй `.describe()` и не включай коллекцию/поле в `COLLECTIONS` (шаг 4). Собственно Zod-схема при этом всё равно может существовать для внутреннего typechecking — see `SITE.address.*` в `config/site.ts`, которые остаются в конфиге, а не в контенте, именно по этой причине.
- Экспортируй `z.infer` тип рядом со схемой — компоненты берут типы отсюда, а не дублируют интерфейсы.

## Шаг 2 — JSON-контент: массив vs синглтон

Два паттерна, выбирай по смыслу:

### Массив (список с произвольным числом элементов)

Файл — JSON-массив объектов, у каждого обязателен `id`:

```json
[
  { "id": "advantage-1", "icon": "M12 2 4 7v10l8 5 8-5V7z", "title": "…", "description": "…" }
]
```

`file()`-loader Astro сохраняет порядок массива — **специально нет поля
`order`**: перетаскивание строки в списке CMS переписывает массив и меняет
порядок на сайте автоматически.

### Синглтон (ровно один экземпляр)

Файл — JSON-объект с одним (или несколькими фиксированными) строковым
ключом:

```json
{ "aggregate": { "value": 4.9, "count": 0 } }
```

```json
{ "main": { "badge": "…", "title": "…", "subtitle": "…" } }
```

Ключ (`aggregate`, `main`) — это `singletonKey`, читается как
`getEntry('rating', 'aggregate')`. По конвенции этого проекта ключ — почти
всегда `'main'`; `rating` использует `'aggregate'` по историческим причинам
(не переименовывай без причины — смена ключа ломает уже сохранённые ссылки
на портале).

**Когда группировать несколько логических блоков в один синглтон** (как
`sections` — заголовки восьми секций главной, или `pages` — тексты трёх
второстепенных страниц): если поля образуют один смысловой экран в портале
(«Тексты разделов», «Тексты страниц») и не имеют смысла как отдельные CMS-
коллекции. Тогда поле адресуется dot-путём: `sections::intro.title`,
`pages::about.heading.subtitle`. `fd-edit.js` умеет резолвить точечный путь
(`getByDotPath`) из коробки — ничего в оверлее менять не нужно.

**Синглтон с фиксированными полями vs массив с id** — оба варианта валидны
для «фиксированного набора именованных вещей» (например, пункты меню):
массив уместен, если порядок/состав реально может меняться через CMS
(drag-n-drop переставит массив); синглтон с именованными ключами уместен,
если состав жёстко задан вёрсткой и меняться не должен (пять пунктов шапки —
дизайн, не контент). В этом репо для меню и футера выбран **синглтон с
именованными ключами** (`navigationSchema.menu.about/services/...`,
`footerSchema.columns.sections.links.home/about/...`) — см. §«Хрестоматийные
примеры» ниже. Если решишь иначе для нового блока — задокументируй выбор
комментарием в схеме, как сделано там.

### Где живёт файл

- Контент главной страницы — `src/content/home/*.json` (уже используется:
  `features.json`, `reviews.json`, `pricing.json`, `faq.json`, `rating.json`,
  `hero.json`, `sections.json`, `showcase.json`, `team.json`, `stats.json`,
  `partners.json`, `timeline.json`).
- Контент шапки/футера/адреса (сквозной, на каждой странице) —
  `src/content/nav/*.json` (`navigation.json`, `footer.json`,
  `address.json`).
- Тексты второстепенных страниц (не своя `sections`-коллекция) —
  `src/content/pages/pages.json` (один синглтон, ключ `main`, вложенные
  объекты `about`/`contacts`/`gallery`).
- Новая страница со своим набором блоков — заведи `src/content/<page>/*.json`
  по аналогии с `home/`, а не сваливай всё в `pages.json`, если объём
  сопоставим с главной.

**НЕ меняй существующие видимые тексты при переносе в JSON** — копируй их
как есть. Если правишь существующий компонент, дифф в JSON должен быть
`git diff --stat` равен нулю по видимому контенту: та же строка, тот же
смысл, просто теперь строка живёт в файле, а не в `.astro`.

## Шаг 3 — Коллекция в `src/content.config.ts`

```ts
import { file } from 'astro/loaders';
import { featureSchema } from './config/schemas';

const features = defineCollection({
  loader: file('src/content/home/features.json'),
  schema: featureSchema,
});

export const collections = { /* …остальные, */ features };
```

Один `defineCollection` на файл, независимо от того, массив это или
синглтон — Astro сам определяет форму по содержимому файла. После правки
**обязательно** прогони `npx astro sync`, иначе `astro:content` не увидит
новых типов и `astro check`/сборка будут падать с «Argument of type ... is
not assignable to parameter of type 'keyof DataEntryMap'».

## Шаг 4 — Регистрация в контракте (`scripts/generate-content-schema.ts`)

Это единственное место, которое решает, что из `content.config.ts`
**доступно клиентскому CMS-порталу** — это allowlist, не 1:1 с
`collections` (например `blog` там сознательно отсутствует, см.
`docs/CONTENT.md`).

```ts
{
  name: 'features',
  label: 'Преимущества', // русское имя коллекции в списке портала
  schema: featureSchema,
  filePath: 'src/content/home/features.json',
  kind: 'array',
},
```

Для синглтона добавь `kind: 'singleton'` и `singletonKey: 'main'` (или
другой ключ, если он не `'main'`).

`label` — **обязательное** поле (без него портал покажет системное имя
коллекции вместо человеческого). Каждая новая коллекция = одна новая запись
в массиве `COLLECTIONS` + при желании обновление комментария-allowlist
сверху файла.

После правки — перегенерируй и закоммить контракт:

```bash
npx tsx scripts/generate-content-schema.ts   # переписывает content.schema.json
```

`scripts/__tests__/generate-content-schema.test.ts` сверяет закоммиченный
файл со свежей генерацией и падает с понятной подсказкой, если забыть этот
шаг.

## Шаг 5 — Разметка `data-cms` в компоненте

### Формат атрибута

```
data-cms="<collection>:<itemId>:<field>"
```

- `collection` — имя из `content.config.ts`/`COLLECTIONS`, ровно как есть.
- `itemId` — стабильный `id` элемента массива; **пустая строка** для
  синглтонов (`collection::field` — два двоеточия подряд).
- `field` — имя поля; может быть **dot-путём** (`cta.label`,
  `about.heading.title`) для вложенных объектов.

Итого в значении ровно два двоеточия (`value.split(':').length === 3`) —
это единственное, что жёстко проверяет
`scripts/__tests__/annotations.test.ts` («no malformed data-cms
attributes»). Dot-путь внутри поля не считается — двоеточие там не ставится
никогда.

### На какой элемент вешать атрибут

**Правило номер один: атрибут ставится на элемент, чей `textContent`
ЦЕЛИКОМ и ТОЧНО равен значению поля.** `fd-edit.js` в режиме правки делает
`el.textContent = String(val)` — если внутри элемента есть что-то ещё
(другой текст, дочерние теги, пунктуация), правка это стирает.

Отсюда конкретные правила:

1. **Никогда не вешай `data-cms` на элемент с дочерней разметкой** (SVG,
   вложенные теги, иконки). Если такой элемент есть, оберни именно
   текстовый узел в `<span>` и вешай атрибут на `<span>`.

2. **Для ссылок и кнопок — `<span data-cms=...>` ВНУТРИ `<a>`, никогда на
   самом `<a>`.** Иначе правка текста снесёт всю внутреннюю разметку ссылки
   (а иногда и её функциональность, если внутри есть иконка).

   ```astro
   <!-- правильно -->
   <a href={PRIMARY_CTA.href} class="btn btn-primary">
     <span data-cms="navigation::ctaLabel">{NAV.ctaLabel}</span>
   </a>

   <!-- НЕПРАВИЛЬНО — data-cms прямо на <a> -->
   <a href={PRIMARY_CTA.href} data-cms="navigation::ctaLabel">{NAV.ctaLabel}</a>
   ```

3. **Пунктуация вокруг значения — СНАРУЖИ аннотированного элемента.**
   Кавычки-ёлочки, слэши, разделители — не должны попасть в
   `textContent` поля, иначе они улетят в сохранённое значение при первой же
   правке.

   ```astro
   <!-- правильно: «» снаружи span -->
   <blockquote>«<span data-cms={`reviews:${r.id}:text`}>{r.text}</span>»</blockquote>

   <!-- НЕПРАВИЛЬНО -->
   <blockquote data-cms={`reviews:${r.id}:text`}>«{r.text}»</blockquote>
   ```

4. **Не вешай голый `data-cms` (textContent-замену) на нетекстовые поля.**
   Булевы флаги (`featured`), числа, используемые не как видимый текст, —
   эти поля по-прежнему описаны в Zod-схеме и редактируются через форму
   портала, просто без click-to-edit разметки на странице. Тот же принцип —
   для иконки преимущества (`features.icon`): она рендерится либо как
   `<svg><path d={f.icon} /></svg>`, либо как эмодзи в `<span>`; в обоих
   случаях `data-cms` **не ставится** — замена `textContent` сломала бы SVG
   (`d` — атрибут, не текст), а условный рендеринг между двумя ветками
   сделал бы клик ненадёжным. Иконка при этом полностью редактируема
   через форму (поле есть в схеме и в контракте) — просто не по клику.

   Путь-к-файлу поля (`showcase.image`) — исключение: они кликабельны через
   `data-cms="<collection>:<id>:<field>"` + `data-fd-attr="src"` на самом
   `<img>` (см. `StackedShowcase.astro`) — тот же приём, что уже используют
   телефонные ссылки (`data-fd-attr="href"` + `data-fd-attr-template` в
   Header/Footer/MapSection/MobileStickyCTA/contacts/thanks). `data-fd-attr`
   патчит именно атрибут, а не `textContent`, так что правило выше про
   SVG/иконки к нему не относится. Значение поля в контенте — не URL, а
   **ключ реестра** (`cms/<uuid>.png` в `src/assets/cms/`); рендерится он
   через `ContentImage.astro` (`src/components/ui/ContentImage.astro`),
   который резолвит ключ в реальный хешированный `astro:assets`-путь на
   сборке (см. «Приложение — оверлей `fd-edit.js`» про гвард, не дающий
   подставить ключ в живой `src` из портала). Папка загрузок объявлена в
   контракте: `uploads: { dir: 'src/assets/cms', valuePrefix: 'cms/' }` в
   сгенерированном `content.schema.json`. На стороне схемы поле помечено
   `.meta({ format: 'image' })` (see
   `showcaseSlideSchema.image`), что кладёт `"format": "image"` в тот же
   `content.schema.json` — **любой новый `format` здесь обязан завести
   парный `ajv.addFormat(...)` в
   `client-portal/src/services/content-service.ts`**, иначе портал не
   сможет скомпилировать схему и публикация сломается для всех коллекций
   клиента, не только для новой.

5. **Один элемент — одно поле.** Не пытайся склеить два поля в один
   `data-cms` («заголовок + подзаголовок одной строкой») — заведи два
   элемента.

6. **Одно поле может встречаться в разметке несколько раз** (например,
   `navigation::phone` показан и в шапке, и в футере, и в блоке карты) —
   это нормально, каждое вхождение получает тот же атрибут; правка в
   портале обновит все сразу при следующей отрисовке.

### Однострочный формат

Держи связку тег+атрибут+интерполяция на одной строке там, где это не
портит читаемость:

```astro
<h2 class="text-3xl font-bold md:text-4xl" data-cms="sections::cta.title">{title}</h2>
```

Перенос `{title}` на отдельную строку не сломает ничего технически (браузер
схлопывает whitespace, а `fd-edit.js` перезаписывает `textContent`
целиком при правке), но плодит визуальный шум и расходится с существующим
кодом — не делай так без причины.

### Переиспользуемые компоненты на нескольких страницах

Компонент вроде `IntroSection`/`FeaturesSection` используется и на главной
(со своими текстами из `sections`), и на `/about/` (со своими текстами из
`pages.about`). Захардкоженный `data-cms="sections::intro.eyebrow"` внутри
компонента был бы **неверным** на странице `/about/` — там показан другой
текст, но атрибут указывал бы не на тот источник.

Решение — компонент принимает `cmsScope` (строка вида
`"<collection>::<fieldPrefix>"`), по умолчанию равный старому поведению, и
строит атрибуты из него:

```astro
---
interface Props {
  eyebrow?: string;
  title?: string;
  body?: string;
  /** collection::field-префикс для data-cms; переопредели, когда компонент
   *  используется на другой странице со своим источником текста. */
  cmsScope?: string;
}
const { eyebrow = T.eyebrow, title = T.title, body = T.body, cmsScope = 'sections::intro' } = Astro.props;
---
<p data-cms={`${cmsScope}.eyebrow`}>{eyebrow}</p>
<h2 data-cms={`${cmsScope}.title`}>{title}</h2>
<p data-cms={`${cmsScope}.body`}>{body}</p>
```

```astro
<!-- about.astro -->
<IntroSection
  eyebrow={PAGE.intro.eyebrow}
  title={PAGE.intro.title}
  body={PAGE.intro.body}
  cmsScope="pages::about.intro"
/>
```

**`cmsScope` уже реализован во всех секциях с заголовками:** `IntroSection`,
`FeaturesSection`, `PricingSection`, `ReviewsSection`, `GallerySection`,
`MapSection`, `FAQSection`, `CTASection`, а также `PageHero` (там он
**необязательный**: без него компонент вообще не печатает `data-cms` — это
верный ответ для страниц, чей заголовок задан вёрсткой, а не контентом).
Заводя новый компонент с заголовком — добавляй `cmsScope` сразу, по этому же
образцу.

Две границы, о которых надо помнить:

- **`cmsScope` скоупит только заголовочные тексты.** Карточки внутри
  (тарифы, отзывы, вопросы) приходят из своей коллекции, и их item-level
  атрибуты (`pricing:<id>:name`) жёстко привязаны к ней. Передать в такой
  компонент `items` из ДРУГОЙ коллекции — значит проставить им неверный
  источник; для этого случая пишется отдельный компонент.
- **Компонент, чьи поля лежат плоско в собственном синглтоне**
  (`HeroSection` → `hero::title`), скоупу не поддаётся: у него нет
  dot-префикса. Нужен второй «первый экран» с другим текстом — заводи для
  него отдельный блок в `pages`/свою коллекцию, а не переиспользуй `hero`.

## Шаг 6 — Рот-гвард (`scripts/__tests__/annotations.test.ts`)

Тест — это две карты + проверка формата, читающие собранный `dist/*.html`
(запускается после `npm run build`, отдельно — `vitest run` без билда
ничего не найдёт):

- **`VISUAL_FIELDS`** — коллекции-массивы; для каждого `id` из
  `src/content/home/<collection>.json` (см. `itemIds()`) и каждого поля из
  списка ожидается `data-cms="<collection>:<id>:<field>"` в HTML.
- **`SINGLETON_FIELDS`** — синглтоны, которые рендерятся **на каждой
  странице** (Header/Footer — сквозная навигация/футер/адрес — или
  hero/sections, которые проверяются на главной). Проверяются по `dist/index.html`.
- **`ROUTE_SINGLETON_FIELDS`** — синглтоны, чьи поля видны только на
  конкретном маршруте (сейчас — `pages.about.*`/`pages.contacts.*`/
  `pages.gallery.*`). Ключ — путь `dist/<route>/index.html`, значение — та
  же форма, что `SINGLETON_FIELDS`, но проверяется только на этом файле.
  **Заводя новую нехоумную страницу с CMS-полями — добавь сюда её
  `dist/<page>/index.html` и список полей**, иначе рот-гвард её не увидит
  (по умолчанию тест смотрит только на `dist/index.html`).

При добавлении нового поля/коллекции — **всегда** дополни соответствующую
карту. Тест специально спроектирован так, чтобы рефакторинг компонента,
случайно снёсший `data-cms`, ронял `npm test`, а не проходил тихо.

## Третий вид коллекции: `entries` (файл-на-запись)

Всё выше (Шаги 1–7) описывает `array`/`singleton` — один JSON-файл на
коллекцию. Каталог товаров (2026-08-01) ввёл третий вид: **`entries`** —
одна запись = один файл `<dir>/<slug><ext>` (frontmatter + опциональное
markdown-тело), а не строка внутри общего JSON. Живой пример в этом репо —
`products` (`src/content/products/*.md`).

### Когда заводить `entries`, а не `array`

`array` подходит, когда позиций разумное число и все они помещаются в один
JSON-файл (тарифы, отзывы, FAQ — десятки записей максимум). `entries`
нужен, когда:

- у каждой записи есть **своя страница сайта** (SEO-адрес, метатеги,
  собственный маршрут) — не просто карточка в списке;
- запись может нести **длинное тело** (markdown/MDX), которое неудобно
  хранить строкой в JSON-массиве;
- записей может стать много (десятки-сотни) — один растущий JSON-файл на
  все товары/статьи стал бы неудобной единицей конфликтов при коммитах
  портала.

### Контракт: блок `entries`, не `collections`

`content.schema.json` получает **отдельное** верхнеуровневое поле
`entries` (аддитивное — `version` контракта остаётся `1`; порталы на
прежней версии контракта его не видят и продолжают работать с
`collections` как раньше — это осознанно защищённая совместимость, см.
`ContentSchemaDocument.entries?` в генераторе):

```jsonc
// content.schema.json
{
  "version": 1,
  "collections": { /* … array/singleton, как раньше … */ },
  "entries": {
    "products": {
      "label": "Каталог товаров",
      "dir": "src/content/products",
      "ext": ".md",
      "routeBase": "/katalog",
      "body": { "enabled": true, "format": "markdown", "label": "Подробное описание (необязательно)" },
      "itemSchema": { /* JSON Schema фронтматтера, как itemSchema у обычной коллекции */ }
    }
  }
}
```

- `dir` — каталог файлов записи (относительно корня репозитория); `ext` —
  расширение файла (`.md`, см. ниже почему не `.mdx`). Путь записи **всегда**
  `<dir>/<slug><ext>` — портал не принимает произвольный путь от клиента.
- `routeBase` — префикс маршрута на сайте (`/katalog`), нужен порталу
  только для построения ссылки-превью «Открыть страницу ↗»; сама
  маршрутизация (какой сегмент пути после `routeBase` строится из
  категории/слага) — забота astro-starter, не контракта.
- `body` — есть ли у записи markdown-тело ниже frontmatter, и его лейбл в
  форме портала. Сам блок `body` в контракте обязателен (`EntriesContract`
  не делает его опциональным полем) — вариативна только его начинка:
  `enabled: false` означает «запись только frontmatter, без тела».

### В генераторе (`scripts/generate-content-schema.ts`)

`entries` собирается отдельным массивом-конфигом `ENTRIES` (не
`COLLECTIONS` — они формируют разные ветки `ContentSchemaDocument`):

```ts
const ENTRIES = [
  {
    name: 'products',
    label: 'Каталог товаров',
    schema: productSchema,          // тот же Zod, что у array/singleton
    dir: 'src/content/products',
    ext: '.md',
    routeBase: '/katalog',
    body: { enabled: true, format: 'markdown' as const, label: 'Подробное описание (необязательно)' },
  },
];
```

`buildContentSchema()` наполняет `entries[e.name].itemSchema` тем же
`z.toJSONSchema(e.schema)`, что и обычные коллекции — Шаг 1 (Zod-схема,
`.describe()` на каждом поле) не меняется ни на йоту для `entries`.

### `.md`, никогда не `.mdx` — для тел, которые редактирует клиент

**Решение владельца, зафиксированное после ревью:** тело записи `entries`,
которое правит клиент через простую markdown-textarea портала, хранится в
файле `.md`, не `.mdx`.

Причина — не стилистическая, а функциональная: **MDX исполняет содержимое
тела как JS-выражения на сборке.** `{выражение}`, `export const foo = …`,
JSX-теги — всё это парсится и выполняется компилятором Astro при `npm run
build`. Простое, ничем не защищённое клиентское тело:

- содержащее `{` не как часть текста, а похожее на JS-синтаксис — падает
  сборку с непонятной для нетехнического человека ошибкой компилятора;
- содержащее одинокий `</` (например, в описании «размер `<`10 см, разрез
  `</`» или просто опечатку) — тоже валит сборку (MDX ждёт закрывающий тег).

`.md` этих проблем не имеет: markdown-парсер не исполняет код, `{`/`</` —
обычные символы текста. Модель доверия та же, что у остального контента
клиента (плохой ввод портит только отображение, никогда не ломает сборку).

**Когда `.mdx` уместен** — только если тело производит **контролируемый
редактор**, который сам гарантирует валидный вывод (кастомные JSX-блоки
сериализуются предсказуемо, произвольный текст не долетает до компилятора
буквально). Волна блога (Plate, см. `Freim Deploy` ROADMAP «Каталог/блог —
волна C») планирует именно такую связку — MDX там оправдан, потому что
редактор, а не голая textarea, контролирует форму вывода. **Заводя новую
`entries`-коллекцию с телом, редактируемым простой текстовой formой —
используй `.md`. Если тянет использовать `.mdx` для клиентского тела без
такого редактора и без санитайзера — это тот самый риск, из-за которого
каталог сделан на `.md`; не повторяй эту ошибку.**

### Чего у `entries` НЕТ (в отличие от Шагов 5–6)

- **Нет `data-cms`-разметки и click-to-edit.** Записи `entries`
  редактируются только через отдельный экран портала (для каталога —
  «Каталог»), не через клик по живой странице. Причина — click-to-edit для
  many-file коллекции с собственными маршрутами требует доработки
  Editor-экрана портала, отложено до волны блога (см. спеку §1.4). Шаг 5 и
  рот-гвард Шага 6 (`annotations.test.ts`) `entries`-коллекции не касаются
  вообще — их не нужно туда добавлять.
- **Портал не показывает `entries`-коллекции в общем сайдбаре Editor.**
  Фильтр `kind === 'array' || kind === 'singleton'` на стороне портала
  сознательно исключает `entries` (и любой будущий неизвестный `kind`) из
  формы-по-схеме — у них свой экран.

### Демо-контент и тесты

- Демо-каталог (`src/content/catalog/categories.json` + 3 `.md`-товара в
  `src/content/products/`) — часть шаблона, чтобы у нового сайта каталог
  работал из коробки и было что редактировать в e2e.
- Глубина дерева категорий (`array`-коллекция `categories`, поле `parent`)
  ограничена **строго 2 уровнями**: `assertCategoryDepth()` в генераторе
  бросает при сборке, если у категории с `parent` сам родитель тоже
  `parent`-имеет (глубина 3+), или `parent` ссылается на несуществующий id.
- `src/lib/catalog.ts` — тестируемая логика построения маршрута
  (`buildCatalogPaths`), покрыта `src/lib/__tests__/catalog.test.ts`: все
  уровни (категория → подкатегория → товар), `draft: true` исключается из
  `getStaticPaths`, товар со ссылкой на несуществующую категорию — понятная
  ошибка сборки (не тихий пропуск).
- Тест генератора (`scripts/__tests__/generate-content-schema.test.ts`)
  проверяет форму блока `entries` (`label`, `dir`, `ext`, `routeBase`,
  `body`) так же, как rot-guard проверяет `collections`.

## Типичные ошибки (и как их избежать)

1. **Забыть `npx astro sync` после правки `content.config.ts`.** Симптом:
   `astro check`/сборка ругаются `Argument of type "foo" is not assignable
   to parameter of type 'keyof DataEntryMap'` на все новые `getEntry`/
   `getCollection` вызовы. Лечится одной командой.

2. **`data-cms` прямо на `<a>` вместо `<span>` внутри неё.** Правка текста
   в портале сотрёт остальную разметку ссылки при следующей записи
   `textContent`.

3. **Кавычки/пунктуация внутри аннотированного элемента.** Первая же правка
   в портале унесёт их в сохранённое значение поля — а на следующей
   отрисовке кавычки появятся ещё раз (задвоятся) или пропадут вовсе, в
   зависимости от того, что редактор впишет.

4. **Забыть шаг 4 (регистрация в `COLLECTIONS`).** Коллекция технически
   работает на сайте, но невидима для CMS-портала — клиент не может её
   редактировать, хотя по коду выглядит так, будто должен.

5. **Забыть перегенерировать `content.schema.json`.**
   `generate-content-schema.test.ts` ловит это автоматически — падает с
   инструкцией, какую команду прогнать.

6. **Захардкоженный `cmsScope` в общем компоненте, используемом на
   нескольких страницах с разными данными.** Клик по тексту на `/about/`
   будет редактировать поле, которое реально отображается на главной —
   тихая порча данных, которую не ловит ни один тест (потому что HTML
   технически валиден, просто атрибут указывает не туда). Смотри «Шаг 5 →
   переиспользуемые компоненты».

7. **Дублирование строки контента и в JSON, и как хардкод-дефолт в
   `.astro`/`.ts`.** Каждое поле обязано рендериться из коллекции — если
   нужен дефолт на случай отсутствия записи, это баг схемы (все поля здесь
   обязательные не-опциональные строки), а не повод хардкодить копию
   текста в компоненте.

8. **Смена/переиспользование существующего `id` или `singletonKey`.**
   Ссылки «эта карточка в CMS ↔ этот `id` в JSON» уже могли быть сохранены
   на портале или во внешних интеграциях. Добавляй новые `id`, никогда не
   меняй и не удаляй старые без явного запроса на миграцию данных.

9. **Вынос в CMS поля, которое питает JSON-LD или влияет на `href`/`tel:`/
   `mailto:`.** Плохая правка там не портит текст, а ломает рабочую ссылку
   или выдачу в поиске. В контент выносится только отображаемая копия —
   полная таблица «что остаётся в коде, что уходит в контент и почему» в

## Приложение — оверлей `fd-edit.js` и его протокол

Обычно этот файл трогать не нужно: он самодостаточен и не зависит от
конкретных коллекций. Но если разработчик меняет связку «портал ↔ сайт», вот
контракт, который обе стороны обязаны соблюдать (портальная половина —
`client-portal/frontend/src/overlay-bridge.ts` в репо Freim Deploy).

### Сообщения

`fd-edit.js` активируется, только когда страница открыта **в iframe** и есть
либо `?fd_edit=1&fd_origin=<origin портала>`, либо ранее сохранённый ключ
`fdEdit.origin` в `sessionStorage` (см. ниже). Сообщения принимаются только с
`fd_origin`; портал, в свою очередь, принимает только с origin своего
`siteUrl` из БД.

**Сайт → портал** `{source:'fd-edit', type, …}`:

| type | Поля | Смысл |
|------|------|-------|
| `ready` | — | Хендшейк. Повторяется каждые 250мс (до 40 попыток), пока портал не ответит `init` — лечит гонку загрузки iframe. Шлётся заново на каждой загрузке страницы. |
| `select` | `path` | Клик по элементу `[data-cms]` в режиме правки. |
| `edit` | `path, value` | (зарезервировано) правка прямо на странице. |
| `url` | `href` | `location.pathname` текущей страницы — шлётся на каждой загрузке, чтобы портал показал, какая страница открыта, и сбросил выделение. |

**Портал → сайт** `{source:'fd-portal', type, …}`:

| type | Поля | Смысл |
|------|------|-------|
| `init` | `values` | Засеять/пересеять весь редактируемый текст. |
| `apply` | `path, value` | Живо переписать `textContent` одного поля. |
| `focus` | `path` | Проскроллить к элементу и подсветить его. |
| `mode` | `editing:boolean` | Режим правки (оверлей включён, клики перехватываются) vs предпросмотр (оверлей снят, сайт ведёт себя как для обычного посетителя). Шлётся сразу после каждого `init`. |

`apply`/`init` для элемента с `data-fd-attr="src"` патчат атрибут только
значением-URL (`data:`, `blob:`, `http(s):`, `/…`). Значение-ключ реестра
(`cms/<uuid>.png`) игнорируется: настоящий адрес такой картинки выдаёт
astro:assets на сборке, портал его не знает, и подстановка ключа стёрла бы
рабочую картинку в превью. Картинка в iframe обновляется после публикации и
пересборки; живое превью только что выбранного файла приходит `data:`-URL-ом.

`path = {collection, itemId|null, field}` (`field` — dot-путь).

### Режим правки vs предпросмотр (паттерн TinaCMS quickEditEnabled)

В предпросмотре `fd-edit.js` целиком снимает свой `<style>` и не перехватывает
клики — ссылки, аккордеоны и переходы между страницами работают штатно. В
режиме правки стиль возвращается, клик по `[data-cms]` выделяет поле в
панели. До прихода первого `mode` по умолчанию `editing=true` (портал шлёт
`mode` сразу после `init`); последний режим кэшируется в `sessionStorage`
(`fdEdit.mode`), чтобы переход между страницами в предпросмотре не мигал
оверлеем.

### Режим переживает навигацию (`sessionStorage`)

При активации `fd-edit.js` сохраняет `fd_origin` в `sessionStorage`
(`fdEdit.origin`). Инлайн-лоадер в `BaseLayout.astro` грузит скрипт, если
страница в iframe И (есть `?fd_edit=1` ИЛИ есть этот ключ). Это позволяет в
предпросмотре кликнуть ссылку → перейти на `/about/` без query-параметров →
оверлей снова активен. `sessionStorage` ограничен **этой вкладкой и origin
самого сайта** и не расшаривается между вкладками/origin — он не расширяет
принятый риск доверия `fd_origin`-из-query, а лишь позволяет уже
активированной вкладке помнить значение, которое она сама приняла из своего
query. Soft-навигация Astro (view transitions) обрабатывается через
`astro:page-load`: DOM пересканируется, `url`/`ready` шлются заново.
