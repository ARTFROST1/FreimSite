# IMAGES.md — как устроена система картинок

Полная справка по тому, как картинки попадают на сайт, что с ними происходит
на сборке, какие типы поддерживаются и где проходят границы. Читается целиком
за 10 минут.

Смежное: [recipes/images-assets.md](recipes/images-assets.md) (рецепты и LQIP),
[CMS-BUILDING.md](CMS-BUILDING.md) (как заводить редактируемые блоки),
[PERFORMANCE.md](PERFORMANCE.md) (бюджеты и LCP).

---

## 1. Главное правило

| Куда положить | Что с ней будет |
| --- | --- |
| `src/assets/**` | Astro (`astro:assets` + sharp) на сборке ресайзит, конвертирует в webp, генерирует `srcset`, подставляет `width`/`height`, кладёт в `dist/_astro/` с хешем в имени (вечный кэш) |
| `public/**` | отдаётся как есть, байт в байт, по стабильному URL |

**Нужен стабильный внешний URL — `public/`. Всё остальное — `src/assets/`.**

Что остаётся в `public/` и почему:

| Файл | Причина |
| --- | --- |
| `public/og/*` | соцсети требуют неизменный URL и точные 1200×630 |
| `public/favicon.svg`, `favicon.ico`, `favicon-96.png`, `apple-touch-icon.png`, `icons/*`, `logo.png` | браузер, iOS и поисковые роботы запрашивают по фиксированному адресу; собираются из вектора командой `npm run build:icons` |
| `public/site.webmanifest`, `public/robots.txt` | то же |
| `public/fonts/*` | подключаются из CSS, хеш не нужен |
| `public/fd-edit.js` | скрипт визуального редактора, грузится по фиксированному пути |
| `public/images/placeholder.svg` | универсальный фолбэк: на него ссылаются дефолты пропсов и он подставляется при промахе ключа |

## 2. Реестр: «положил файл → он появился»

`src/lib/images/registry.ts` собирает все картинки на сборке одним
`import.meta.glob` и отдаёт три функции:

```ts
asset('cms/photo.png')        // → ImageMetadata | undefined
assetsIn('gallery')           // → [{ name, key, img }] — прямые дети папки, человеко-числовая сортировка
coverIn('products/okna')      // → cover.* если есть, иначе первый по имени
```

**Ключ реестра** — путь от `src/assets/` без ведущего слэша: `cms/photo.png`,
`gallery/01-fasad.webp`, `blog/cover.jpg`.

Расширения, которые попадают в реестр: **`.webp`, `.avif`, `.jpg`, `.jpeg`,
`.png`, `.svg`**. Всё остальное (`.gif`, `.tiff`, `.heic`, `.bmp`) реестр не
видит вообще — файл просто не существует для сайта.

Сортировка человеко-числовая: `2.webp` идёт раньше `10.webp`. Поэтому имена
файлов галереи удобно нумеровать `01-…`, `02-…`.

## 3. Значение поля-картинки в контенте: ровно два вида

Поля в JSON-контенте (их пишет CMS-портал) и во фронтматтере блога:

| Вид значения | Пример | Что делает сайт |
| --- | --- | --- |
| **Ключ реестра** (без ведущего слэша) | `cms/7f3a….png`, `blog/cover.webp` | ищет в реестре → оптимизирует через `astro:assets` |
| **Site-absolute путь** (со слэшем) | `/images/placeholder.svg`, `/og/og-home.jpg` | отдаёт файл из `public/` как есть |

Третьего вида нет. Внешний абсолютный URL (`https://…`) технически проходит
как «отдать как есть», но это не поддерживаемый сценарий для контента.

**Легаси-совместимость.** Значения вида `/images/cms/<uuid>.png` (так писал
портал до переезда) сначала пробуются как ключ `cms/<uuid>.png`. Если файл уже
переехал в `src/assets/cms/` — картинка оптимизируется, хотя значение старое.
Если файл всё ещё в `public/images/cms/` — отдаётся оттуда как есть. Ломаться
нечему в обоих случаях.

**Промах ключа.** Значение `cms/nope.png`, которому не соответствует файл:
сборка **не падает** — в лог уходит
`[images] нет файла src/assets/cms/nope.png — рендерю /images/placeholder.svg`,
на страницу идёт плейсхолдер. Это осознанное правило: контент клиента никогда
не должен ронять сборку.

## 4. Рендер: `ContentImage.astro`

Единственная точка рендера картинки. Принимает и `ImageMetadata` (из реестра),
и строку из контента.

```astro
<ContentImage
  src={item.image}                       {/* ключ, публичный путь или ImageMetadata */}
  alt={item.title}
  widths={[640, 1024, 1600]}             {/* кандидаты srcset */}
  sizes="(min-width: 768px) 90vw, 100vw" {/* обязательно, если есть widths */}
  width={1200} height={800}              {/* для не-растровой ветки, чтобы не скакала вёрстка */}
  loading="lazy"                          {/* дефолт; eager — только для LCP */}
  class="h-full w-full object-cover"
  data-cms="showcase:slide-1:image"      {/* прокидывается на итоговый тег */}
  data-fd-attr="src"
/>
```

Три ветки внутри (`classifyImageSource` в `src/lib/images/resolve.ts`):

1. **Растр из реестра** → `<Image>` из `astro:assets`: webp, `srcset` по
   `widths`, `width`/`height` из метаданных. Ширины больше оригинала
   отбрасываются (апскейла нет); если все запрошенные больше оригинала,
   остаётся одна — оригинальная.
2. **SVG из реестра** → обычный `<img>` с размерами из метаданных. sharp SVG
   не трогает: вектор и так масштабируется.
3. **Публичный путь / внешний URL** → обычный `<img>`; `width`/`height`
   берутся из пропсов, если переданы.

Конфиг: `astro.config.mjs` → `image: { responsiveStyles: false, service: sharp }`.
Глобальный `layout` сознательно не включён — он инжектит инлайновые стили
размеров, которые конфликтуют с Tailwind-утилитами (`h-full w-full object-cover`)
на фоновых картинках. Размеры и `sizes` задаются явно в каждом вызове.

Кто уже переведён на `ContentImage`: `HeroSection`, `IntroSection`,
`GallerySection`, `GalleryGrid`, `Marquee`, `StackedShowcase`, `BlogCard`,
`BlogLayout`.

**React-острова.** `astro:assets` работает только на сборке, в Node, поэтому в
клиентский остров попадают готовые строки: страница `src/pages/gallery.astro`
готовит их через `getImage` и передаёт в `ImageGallery.tsx` как
`{ src, srcSet, sizes, full, width, height, alt }`.

## 5. Папки в `src/assets/`

| Папка | Что там |
| --- | --- |
| `cms/` | загрузки клиента через CMS-портал (`<uuid>.<ext>`) — **руками не трогать** |
| `gallery/` | галерея страницы `/gallery/` — реестр подхватывает автоматически |
| `hero/` | фоны первого экрана |
| `sections/` | картинки секций |
| `showcase/` | слайды, если их кладёт разработчик, а не клиент |
| `blog/` | обложки и картинки статей |

Пустая папка — валидное состояние: `/gallery/` при пустой `src/assets/gallery/`
показывает 12 плейсхолдеров и не падает.

⚠️ **Состав галереи `/gallery/` через портал не редактируется.** Список берётся
из реестра — «положил файл в папку → он появился на странице», это работа
разработчика, а не клиента. Если клиент должен менять фотографии сам, заведите
коллекцию-массив с полем `.meta({ format: 'image' })` по образцу `showcase`
(см. [CMS-BUILDING.md](CMS-BUILDING.md)) — тогда каждая картинка становится
загружаемой из формы портала. То же касается `hero/` и `sections/`.

## 6. Блог

- **Обложка** — поле `image` во фронтматтере: ключ реестра (`blog/cover.webp`,
  файл в `src/assets/blog/`) или публичный путь.
- **`og:image` и JSON-LD** резолвятся отдельно: `BlogLayout` через
  `resolveSocialImage` превращает ключ в реальный адрес (растр — webp до
  1200px, SVG — как есть), потому что соцсетям нужен абсолютный URL, а не ключ.
- **Картинки в теле статьи** — относительным путём от файла статьи:
  `![Подпись](../../assets/blog/01-schema.webp)`. Так их оптимизирует Astro.

## 7. Поток CMS: что происходит, когда клиент меняет фото

```
1. Клиент в портале жмёт «Выбрать файл» → POST /api/content/upload
      валидация: расширение png|jpg|jpeg|webp|svg, MIME из браузера, ≤5 МБ
      файл ложится в /var/lib/frostdeploy-portal/uploads/<clientId>/<uuid>.<ext>
      в черновик пишется значение-плейсхолдер  fd-upload://<uuid>.<ext>
        │
2. Превью до публикации:
      в форме      — blob-URL выбранного файла (живёт в памяти вкладки)
      в iframe сайта — портал шлёт data:-URL сообщением 'apply'
        │
3. Клиент жмёт «Опубликовать»
      портал читает uploads.dir из content.schema.json сайта
        (у этого стартера: src/assets/cms, префикс значения cms/)
      коммит картинки в src/assets/cms/<uuid>.<ext>   ← СНАЧАЛА картинка
      коммит JSON со значением cms/<uuid>.<ext>        ← ПОТОМ контент
      загруженный файл из uploads-папки удаляется
        │
4. Миниатюра в форме после публикации
      GET /api/content/asset?key=cms/<uuid>.<ext>
      портал читает байты из репозитория своим PAT → видно СРАЗУ,
      не дожидаясь пересборки сайта
        │
5. Пересборка и деплой сайта
      astro:assets делает webp+srcset → на странице /_astro/<hash>.webp
```

**Лимиты и валидация загрузки** (сторона портала):

| Что | Значение |
| --- | --- |
| Расширения | `png`, `jpg`, `jpeg`, `webp`, `svg` |
| MIME | `image/png`, `image/jpeg`, `image/webp`, `image/svg+xml` (или пустой, если браузер не прислал) |
| Размер файла | ≤ 5 МБ → иначе «Файл больше 5 МБ» |
| Размер запроса | > 6 МБ обрывается раньше, с тем же сообщением |
| Имя в репозитории | всегда `<uuid>.<ext>`, оригинальное имя не сохраняется |

**Эндпоинт превью** `GET /api/content/asset?key=<ключ>`:

| Ответ | Когда |
| --- | --- |
| 200 | файл найден; `Content-Type` по расширению, `Cache-Control: private, max-age=300`, `ETag` |
| 304 | клиент прислал совпадающий `If-None-Match` |
| 400 | ключ не проходит белый список (`^[A-Za-z0-9][A-Za-z0-9._/-]*\.(png|jpe?g|webp|svg)$`, без `..`, без ведущего слэша) |
| 401 | нет сессии или клиента нет в БД |
| 404 | по ключу в репозитории файла нет |
| 413 | файл больше 10 МБ (проверяется по `Content-Length` до скачивания) |
| 502 | сбой GitHub (протухший токен, лимит запросов, сеть) — клиенту русское сообщение, техника в серверный лог |

Читает строго `src/assets/<ключ>` в репозитории **этого** клиента и его
токеном. Вытащить чужой файл или что-то за пределами `src/assets/` через этот
эндпоинт нельзя.

## 8. Контракт между сайтом и порталом

`content.schema.json` (генерируется, коммитится) объявляет:

```json
{ "version": 1, "uploads": { "dir": "src/assets/cms", "valuePrefix": "cms/" }, "collections": { … } }
```

- Портал читает `uploads` и коммитит туда. Если поля нет (сайт на старой версии
  стартера) — работает по-старому: `public/images/cms` + `/images/cms/`.
- Инвариант, который проверяет портал: `dir` обязан быть равен
  `src/assets/` + `valuePrefix`. Пара, которая ему не удовлетворяет,
  игнорируется целиком (уход на дефолт) — иначе публикация шла бы в одно место,
  а миниатюры читались из другого, молча и без ошибки.

**Порядок выпуска не важен**, обе половины совместимы в обе стороны:

| Сайт | Портал | Что будет |
| --- | --- | --- |
| старый | новый | коммит в `public/images/cms`, значение со слэшем — как раньше |
| новый | старый | коммит в `public/images/cms`; сайт отдаёт картинку из `public/` — рабочую, но неоптимизированную |
| новый | новый | коммит в `src/assets/cms`, значение-ключ, на сайте `/_astro/*.webp` со `srcset` |

## 9. Визуальный редактор (клик по картинке в превью)

`public/fd-edit.js` подставляет значение в атрибут `src` **только если это
похоже на URL**: `data:`, `blob:`, `http(s):` или путь с ведущим слэшем. Ключ
реестра (`cms/x.png`) игнорируется — настоящий адрес картинки выдаёт сборка
(`/_astro/<hash>.webp`), портал его не знает, и подстановка ключа стёрла бы
рабочую картинку.

Практическое следствие: после публикации картинка в iframe **не меняется
мгновенно** — она обновится после пересборки и деплоя. Миниатюра в форме при
этом обновляется сразу (см. §7, шаг 4).

## 10. Команды обслуживания

```bash
npm run dev                          # локальный сервер
npm test                             # сборка + все тесты
npx astro check                      # типы

npm run assets:orphans               # какие файлы в src/assets/cms не используются контентом
node scripts/optimize-images.mjs --dry   # что пережмётся (план работ)
node scripts/optimize-images.mjs         # пережать: public/images, src/assets (кроме cms/), public/og
```

`optimize-images.mjs` **никогда** не трогает `src/assets/cms/**`: он
конвертирует в webp со сменой расширения, а имя файла там — часть значения в
JSON, которое пишет портал; смена расширения порвала бы ссылку.

## 11. Брендовая графика из одного мастера

`npm run build:icons` собирает всю брендовую графику из одного мастер-SVG
(`design/logo-master.svg` в корне репо, либо `LOGO_MASTER=путь`): favicon.svg,
favicon.ico (16/32/48 — браузеры и Яндекс.Вебмастер дёргают его напрямую,
минуя `<link>`), favicon-96, apple-touch-icon, PWA-иконки 192/512/maskable
и `public/logo.png` — растровый логотип ≥112×112 с фоном, на который
ссылается Organization-схема (`src/lib/schema.ts`).

Запускать при старте проекта и при каждой смене логотипа — иначе фавиконка
живёт своей жизнью годами. Перед первым запуском сверьте константы
`PLATE`/`FILL_MAP` в `scripts/build-brand-icons.mjs` с заливками вашего
мастера: неизвестная заливка валит скрипт с ошибкой (это страховка от
молчаливой потери контуров). Мастер держим вне `public/` и `src/assets/` —
подробное «почему» в шапке скрипта.

Сироты (`assets:orphans`) не удаляются автоматически: на картинку может
ссылаться контент из другой ветки. Скрипт только печатает список и объём.

## 11. Известные ограничения и гочи

1. **Файл с картиночным расширением, который не является картинкой, роняет
   сборку.** Проверено: `src/assets/…/x.png`, внутри которого текст, даёт
   `Could not process file … imageMetadata` и `astro build` падает. Это
   происходит на этапе импорта в Vite, раньше любого нашего кода, поэтому
   try/catch не помогает. Через портал такой файл не пройдёт (MIME-проверка),
   но руками закоммитить можно. Лечение: удалить файл (или откатить коммит) —
   ищите в ошибке путь.
   *Обрезанная, но валидная по заголовку картинка при этом собирается
   нормально* — sharp дотягивает, что смог.

2. **`.webp`, внутри которого PNG** (редактор «сохранил как» без конвертации) —
   собирается, но весит как PNG. Ловится `node scripts/optimize-images.mjs --dry`
   (он читает реальные метаданные, а не расширение).

3. **`.gif`, `.heic`, `.tiff`, `.bmp` не поддерживаются нигде** — ни реестром,
   ни загрузчиком портала. Конвертируйте заранее.

4. **Хеш в URL меняется при изменении файла.** Нельзя дать клиенту прямую
   ссылку на `/_astro/…`: после следующей правки этого файла адрес станет
   другим. Для «дай ссылку на картинку» кладите файл в `public/`.

5. **Один eager на страницу.** `loading="eager"` + `fetchpriority="high"` —
   только у одного LCP-кандидата (hero или обложка статьи). Остальное `lazy`,
   иначе мобильный LCP расплывается.

6. **iOS игнорирует нативный lazy** у картинок под `transform`-предком
   (карусели, marquee) — см. `docs/recipes/gotchas.md`.

7. **Ключ реестра нельзя ставить в поля, которые уходят наружу как URL**
   (`ogImage` страницы, JSON-LD, `tel:`/`href`). В блоге это уже сделано
   правильно (`resolveSocialImage`), в новых местах — помните.
