# Контент: как устроен и почему именно так

> Этот шаблон рассчитан на то, что **контент правит заказчик через CMS**, а не
> разработчик в редакторе кода. Отсюда все решения ниже.

**Этот документ отвечает на вопрос «ЧТО является контентом и почему».**
Механика — как физически завести редактируемый блок (схема, `data-cms`,
контракт портала, тесты) — целиком в
[CMS-BUILDING.md](CMS-BUILDING.md) и здесь не дублируется.

## Главное правило

**Ни одна строка, которую может захотеть поменять клиент, не живёт в `.astro`,
`.ts` или `.tsx`.**

Причина техническая, а не эстетическая: **никакая CMS не умеет писать
TypeScript.** Decap, Tina, Directus, Storyblok — все читают и пишут
JSON / YAML / Markdown. Контент в `.ts` редактируется только разработчиком,
даже если он аккуратно вынесен из компонента в отдельный файл.

Поэтому данные лежат в `src/content/`, а не в `src/config/`.

## Где что лежит

| Путь | Что | Кто правит |
|---|---|---|
| `src/content/home/*.json` | Блоки главной: первый экран, заголовки разделов, преимущества, отзывы, тарифы, вопросы, рейтинг, витрина | **клиент через CMS** |
| `src/content/nav/*.json` | Сквозное: подписи меню, футер, отображаемый телефон, адрес одной строкой | **клиент через CMS** |
| `src/content/pages/pages.json` | Тексты страниц «О нас» / «Контакты» / «Галерея» | **клиент через CMS** |
| `src/content/catalog/categories.json` | Дерево категорий каталога (≤ 2 уровня) | **клиент через CMS** (экран Editor, обычная `array`-коллекция) |
| `src/content/products/*.md` | Товары каталога — файл-на-товар, frontmatter + опциональное markdown-тело | **клиент через CMS** (отдельный экран «Каталог» портала — не Editor, не click-to-edit) |
| `src/content/blog/*.mdx` | Статьи блога | клиент (см. «Блог» — способ ещё не выбран) |
| `src/config/schemas.ts` | Zod-схемы: форма данных + типы + подписи форм портала | разработчик |
| `src/config/site.ts` | Название, реквизиты, сырой телефон, адресные компоненты, координаты | разработчик (при запуске) |
| `src/config/seo.ts` | Мета-теги страниц | разработчик |
| `src/config/nav.ts` | **Структура** меню и футера (`id` + `href`) — не подписи | разработчик |

Разделение меню — важный частный случай общего правила: **ссылку двигает
разработчик, текст ссылки правит клиент.** `NAV_MAIN`/`NAV_FOOTER`/
`PRIMARY_CTA` хранят только `id` и `href`; все видимые подписи (включая текст
главной кнопки — он один на шапку, мобильную панель, финальный CTA-блок и
CTA в конце статьи) приходят из коллекций `navigation`/`footer`.

## Схемы — единый источник правды

`src/config/schemas.ts` работает сразу в трёх направлениях:

1. **Валидация на сборке.** Опечатка в поле роняет билд, а не выкатывается
   в прод как `undefined` в разметке.
2. **Типы для компонентов** через `z.infer` — переименовали поле, получили
   ошибку типов, а не пустое место на странице.
3. **Формы CMS** генерируются из схемы. Поэтому имена полей и описания пишем
   по-человечески: их читает нетехнический редактор.

## `content.schema.json` — контракт для внешнего CMS-портала

Генерируется из тех же Zod-схем (`npm run generate:content-schema`, также
запускается автоматически перед `npm run build` через `prebuild`). Файл
**коммитится в репозиторий** — внешний клиентский портал читает его через
GitHub Contents API на текущем HEAD, а не из `dist/`.

Тест `scripts/__tests__/generate-content-schema.test.ts` сравнивает
закоммиченный файл со свежей генерацией — если он не совпадает (кто-то
поправил `schemas.ts` и забыл перегенерировать), `npm test` падает с понятной
подсказкой.

## Поле `id` — не для отображения

У каждой записи есть `id` — стабильный слаг (`basic`, `advantage-1`).
Он **не показывается на сайте**, а нужен чтобы адресовать конкретный блок:
портал и визуальный редактор ссылаются на поле как `pricing:basic:price`
(формат атрибута разобран в [CMS-BUILDING.md → Шаг 5](CMS-BUILDING.md)).

**Никогда не перенумеровывайте существующие `id`** — добавляйте новые. Смена
`id` рвёт связь «эта карточка в CMS ↔ этот блок на сайте» и все уже
сохранённые клиентом правки. То же относится к `singletonKey`.

## Порядок = порядок в файле

`file()` сохраняет порядок элементов JSON-массива. Поэтому:

- **нет поля `order`**, которое надо поддерживать вручную;
- перетаскивание строки в списке CMS переписывает массив и меняет порядок
  на сайте.

## Как добавить новую коллекцию

Пошаговая механика — **[CMS-BUILDING.md](CMS-BUILDING.md)**: цепочка из семи
шагов (схема → JSON → коллекция → регистрация в контракте → `data-cms` в
разметке → рот-гвард → регенерация), выбор «массив vs синглтон», правила
разметки и разбор типовых ошибок. Здесь она сознательно не пересказывается,
чтобы два описания не разъехались.

Одно место, о котором легко забыть и которое стоит запомнить отсюда:
**коллекция, не добавленная в `COLLECTIONS`** (`scripts/generate-content-schema.ts`),
работает на сайте, но невидима клиенту в портале — это allowlist, а не
автоматическое зеркало `content.config.ts`. Так, например, сознательно
исключён `blog` (см. ниже).

## Что НЕ выносить в контент

Не всё, что выглядит текстом, является контентом. **Оставить в коде:**

- тексты валидации и ошибок форм (`ContactForm.tsx`, `LeadForm.astro`) —
  включая экран «отправлено» внутри самого React-острова: это состояние
  формы, а не страница;
- `aria-label`, alt-заглушки, служебные подписи;
- строки 404 и cookie-баннера — меняются раз в жизни.

Клиенту их править незачем, а сломать форму или доступность — легко.

**Исключение, сделанное сознательно (03.09.2026): страница `/thanks/`.** Она
выглядит служебной, но это последний экран воронки — та самая формулировка,
которую клиент хочет подогнать под свой тон («перезвоним за 15 минут»).
Весь её видимый текст переехал в `pages::thanks.*` (заголовок, абзац,
подпись кнопки звонка, ссылка возврата). Режим работы из `SITE.workingHours`
и стрелка «←» дописываются компонентом ВНЕ размеченных элементов — правка в
портале их не съест.

**Главное исключение — значения, которые уходят не на экран, а в машину.**
Всё, что питает ссылку (`href`, `tel:`, `mailto:`) или структурированные
данные (JSON-LD), остаётся в `src/config/`, даже если выглядит как обычная
строка: плохая правка там не портит текст, а ломает рабочую ссылку или
выдачу в поиске. В контент выносится **только отображаемая копия**:

| В коде (`config/site.ts`) | В контенте | Почему так |
|---|---|---|
| `contact.phoneRaw` — `+79000000000` | `navigation.phone` — `+7 (900) 000-00-00` | из первого строится `tel:`, второе просто печатается |
| `address.country/region/locality/street/postalCode` | `address.full` — адрес одной строкой | первые уходят в `LocalBusiness` JSON-LD, вторая только показывается |
| `contact.email` | — | используется и в `mailto:`, и в схеме |
| `href` пунктов меню и `PRIMARY_CTA.href` | подписи из `navigation`/`footer` | ссылку двигает разработчик, текст правит клиент |

Тот же принцип для картинок: ключ реестра (`cms/x.png`) нельзя класть в поле,
которое уходит наружу как URL (`ogImage`, JSON-LD) — см. [IMAGES.md](IMAGES.md).

**Отдельный случай — юридические страницы** (`privacy-policy`,
`soglasie-na-obrabotku-dannykh`, `terms`). Граница проходит ВНУТРИ страницы,
а не по странице целиком:

- **Проза остаётся в коде.** Ошибка в формулировке — юридический риск, а
  тексты вдобавок построчно сверены с реальным поведением сайта (состав
  данных ↔ `lib/lead-form.ts`, метки ↔ `lib/utm.ts`, вебвизор ↔
  `YandexMetrika.astro` — см. [LEGAL.md](LEGAL.md) §3). Отдать прозу
  клиенту — значит потерять эту сверку. Ролей, которыми можно было бы
  разделить «редактор текста» и «редактор документов», в портале нет.
- **Факты оператора клиент правит сам** — коллекция `legal`
  (`src/content/legal/legal.json`, ярлык «Реквизиты в правовых документах»):
  ФИО, ИНН, ОГРНИП, адрес регистрации, ФИО ответственного, даты редакций
  трёх документов, номер и дата уведомления РКН.

Что именно и почему НЕ попало в `legal` (форма юрлица, `mailto:`/`tel:`,
фактический адрес, сроки из 152-ФЗ, блок обработчиков) — доккоммент
`legalSchema` в `src/config/schemas.ts`.

## Каталог

Товары и категории — не `array`/`singleton`, а третий вид коллекции,
`entries` (одна запись = один файл, а не строка внутри общего JSON):
механика полностью разобрана в
[CMS-BUILDING.md → «Третий вид коллекции: `entries`»](CMS-BUILDING.md#третий-вид-коллекции-entries-файл-на-запись).
Здесь — только «кто чем правит»:

- **Категории** (`src/content/catalog/categories.json`) — обычная
  `array`-коллекция, дерево ≤ 2 уровня через поле `parent`. Клиент
  управляет ими на существующем экране Editor, как любым другим списком.
- **Товары** (`src/content/products/*.md`) — `entries`-коллекция. Клиент
  создаёт/редактирует/публикует/удаляет их на отдельном экране «Каталог»
  портала (не через Editor: `entries` сознательно не попадают в
  форму-по-схеме). Со стороны шаблона товары **размечены** `data-cms`
  (`products:<слаг>:title|shortDescription|price`), так что клик по товару на
  живой странице адресует поле; чтобы этот клик открыл товар, портал должен
  уметь роутить коллекцию `products` на свой экран «Каталог» — см.
  [CMS-BUILDING.md → «Click-to-edit у `entries`»](CMS-BUILDING.md#click-to-edit-у-entries--есть-обновлено-03092026).
  Черновик — поле `draft: true` во frontmatter, не отдельное состояние
  портала: товар виден в портале сразу, но не публикуется на сайт, пока
  `draft` не станет `false`.
- **Порядок товаров** — поле `priority` («Порядок», больше — выше), при
  равенстве — по названию русским алфавитом. Порядок файлов на диске ни на
  что не влияет.
- Тело товара — простое markdown-поле в `.md`-файле (не `.mdx` — см.
  предупреждение в CMS-BUILDING.md, почему для клиентских тел без
  контролируемого редактора это принципиально), заполняется опционально.

## Блог

Статьи — MDX в `src/content/blog/`, схема frontmatter в `src/content.config.ts`.

Список статей пагинирован: `/blog/` — первая страница, `/blog/page/N/` —
дальше (`src/pages/blog/page/[page].astro`; `/blog/page/1/` не
генерируется, чтобы не дублировать корень). Размер страницы —
`BLOG_PAGE_SIZE` в `src/config/site.ts`; обе страницы рендерит один
`components/blog/BlogListing.astro`, навигация — `ui/Pagination.astro`
([рецепт](recipes/ui-components.md)).

⚠️ **Ограничение, о котором надо знать заранее.** Если в теле статьи
использовать JSX-компоненты:

```mdx
<ComparisonTable rows={...} />
```

— то markdown-редактор CMS их не поймёт и при сохранении может испортить.
Проверено на боевом проекте: там 4 статьи с `<ComparisonTable>` и `<BlogCTA>`
пришлось исключить из CMS.

### ⚠️ ОТКРЫТЫЙ ВОПРОС — решение не принято

Как именно клиент будет править статьи, **ещё не решено**. Три варианта:

| Подход | Суть | Цена |
|---|---|---|
| **Чистый markdown** | Статьи без компонентов | Самый безопасный, самый бедный |
| **Editor components** | Decap умеет `registerEditorComponent`: компонент показывается редактору как блок с полями, а в файл пишется нужная разметка | Рабочий компромисс, требует кода на каждый компонент |
| **Только frontmatter** | Клиент правит заголовок/описание/обложку, тело — разработчик | Дёшево, но клиент не самостоятелен |

Решение принимается **вместе с выбором CMS** (Decap или Tina — тоже открыто).
Шаблон поддержит любой из вариантов: схема frontmatter и хранение статей
от этого выбора не зависят, меняется только конфигурация CMS.

Контекст и полный ресерч по выбору CMS:
`FrostDeploy/doc/research/cms-visual-editing/`.

## Деплой

В корне лежит `frostdeploy.json` — контракт с панелью деплоя.
Полная спецификация: **`FrostDeploy/doc/FROSTDEPLOY-JSON.md`** (единственный
оригинал, здесь намеренно не дублируется, чтобы не разъезжалось).

Текущее значение для этого шаблона:

```json
{ "kind": "static", "build": { "command": "npm run build", "output": "dist" } }
```

Две вещи, которые важно помнить:

- **`kind` меняется на `node`, если включить node-адаптер** в `astro.config.mjs`
  (гибрид со SSR-роутами или формами). Правило из спеки: «если после сборки
  должен работать процесс — это `node`».
- **Собирать через `npm run build`, а не вызовом `astro build` напрямую.**
  На `build` навешен `postbuild` с IndexNow-уведомлением; голый `astro build`
  его не запустит, и поисковики молча не узнают об обновлении. По той же
  причине проект держится на npm (панель Freim Deploy ставит зависимости
  `npm ci`, как и GitHub Actions): pnpm по умолчанию не выполняет `postbuild`.
