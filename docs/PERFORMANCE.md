# Производительность (Performance)

Шаблон изначально быстрый: статический HTML (SSG), ноль JS по умолчанию,
Tailwind v4 с tree-shaking. Задача — не сломать это при наполнении контентом.

Целевые Core Web Vitals: **LCP < 2.5s**, **INP < 200ms**, **CLS < 0.1**.

---

## 1. Островная архитектура (Islands) и гидратация

Astro по умолчанию рендерит компоненты в чистый HTML **без JS**. React-остров
оживает только там, где вы явно повесили директиву `client:*`.

**Правило: по умолчанию — 0 JS (обычный `.astro`). Остров добавляем только там,
где есть реальная интерактивность.**

Директивы (по «стоимости», от дорогой к дешёвой):

| Директива        | Когда грузится JS               | Применение |
|------------------|----------------------------------|------------|
| `client:load`    | сразу при загрузке страницы      | интерактив «над сгибом», критичный с первого кадра |
| `client:idle`    | когда браузер простаивает        | некритичный интерактив |
| `client:visible` | когда элемент попал во вьюпорт    | всё «под сгибом» |
| `client:media`   | при совпадении media-query       | только мобильный/десктопный виджет |

В этом шаблоне интерактивных островов два, и оба на `client:visible` (грузятся
лениво, только когда пользователь до них доскроллил):

- `src/components/ui/ContactForm.tsx` — форма заявки;
- `src/components/ui/ImageGallery.tsx` — галерея/лайтбокс.

По умолчанию `client:load` не используется нигде — и это правильно. Прежде чем
добавить остров, спросите: «это можно сделать HTML+CSS?». Аккордеон FAQ, мобильное
меню, sticky-CTA сделаны без React.

## 2. Изображения

Картинки — обычно главный источник веса и LCP.

- **Форматы:** WebP или AVIF. AVIF меньше, WebP — совместимее. JPEG/PNG только
  как запасной вариант.
- **По умолчанию — `src/assets/` через `<ContentImage>`, не `public/`.**
  Правило и детали — `docs/recipes/images-assets.md`. Коротко:
  - Всё контентное (hero, секции, галерея, блог, загрузки клиента через
    CMS-портал в `cms/`) лежит в `src/assets/` и рендерится через
    `<ContentImage src={…} alt={…} widths={…} sizes={…} />`
    (`src/components/ui/ContentImage.astro`) — единая точка: растр уходит в
    `<Image>` из `astro:assets`, публичный путь и SVG — в обычный `<img>`.
    `srcset` компонент строит сам, обрезая переданные `widths` по реальной
    ширине оригинала (нет апскейла и лишних байт); дефолт — `[400, 800,
    1200, 1600]`.
  - `public/` — только для того, чему нужен стабильный внешний URL: OG-картинки,
    favicon, шрифты, `robots.txt` и подобное. Такие файлы отдаются как есть,
    без оптимизации.
  - Глобальная опция `image.layout` (`astro.config.mjs`) **не задана** —
    она инжектит инлайновые стили размеров, которые конфликтуют с
    Tailwind-утилитами (`h-full w-full object-cover`) на фоновых картинках
    стартера. Ширины задаёт сам `<ContentImage>` явным пропом `widths`.
- **Размеры обязательны.** Всегда задавайте `width`/`height` (или aspect-ratio
  в CSS), иначе страница «прыгает» → плохой CLS. Растр и SVG из реестра
  `<ContentImage>` проставляет сам из метаданных; для публичного пути
  (`/images/...`, например дефолтный `placeholder.svg`) размеров у файла нет —
  передавайте `width`/`height` явными пропсами `<ContentImage>`.
- **Ленивая загрузка:** для картинок под сгибом — `loading="lazy"` (дефолт
  `<ContentImage>`).
- **LCP-герой:** ровно ОДИН eager-кандидат на страницу — картинка первого
  экрана (hero, обложка статьи) — получает `loading="eager"
  fetchpriority="high"` явным пропом `<ContentImage>`, всё остальное
  остаётся lazy.

## 3. Шрифты

Дефолт шаблона — системный стек (`--font-heading` / `--font-body` в
`src/styles/global.css` `@theme`), поэтому шрифты вообще ничего не грузят.
Для брендового шрифта — **самохостинг**, без Google Fonts (быстрее, приватнее,
меньше вопросов по 152-ФЗ/GDPR).

Порядок (см. `src/assets/fonts/README.md`):

1. Скачать WOFF2 (для variable-шрифта — один файл на все начертания). Диапазон
   весов брать максимальный доступный: при более узком браузер молча откатится
   на ближайший вес, и заголовочные 900 отрисуются жиже, чем задумано.
2. **Сабсетить** под latin + cyrillic (`glyphhanger`/`fonttools`) — экономия 3–5×.
   Латиница под нелатинский контент обычно можно урезать сильнее готовых
   подмножеств — команда пересборки под фактический набор глифов и правило
   «набор глифов и `unicode-range` меняются вместе» — в
   `src/assets/fonts/README.md`.
3. Положить `.woff2` в **`src/assets/fonts/`**, не в `public/`. Адаптер
   `@astrojs/node` ставит `Cache-Control: immutable` только на `/_astro/*`;
   из `public/` шрифт ревалидируется на каждом переходе — два лишних round-trip
   к рендер-критичному ресурсу. Через Vite он получает хеш в имени, попадает
   в `/_astro/` и кэшируется на год. (Для чисто статического деплоя без
   адаптера это тоже верно: правила кэша хостов обычно заточены на `/_astro/`.)
4. Добавить `@font-face` в `global.css` относительным путём
   (`url('../assets/fonts/…')`), указать `font-display: swap` и навести на него
   `--font-heading` / `--font-body`.
5. **Preload** критичного подмножества — в `src/layouts/BaseLayout.astro`:
   импорт `?url` рядом с остальными и `<link>` в `<head>`. Путь обязан прийти
   из того же импорта, иначе preload и `@font-face` укажут на разные URL и
   браузер скачает шрифт дважды.
   ```astro
   import brandCyrillicUrl from '../assets/fonts/brand-cyrillic.woff2?url';
   ...
   <link rel="preload" as="font" type="font/woff2"
         href={brandCyrillicUrl} crossorigin="anonymous" />
   ```

`font-display: swap` обязателен — текст не блокируется на загрузке шрифта.

## 4. CSS

Tailwind v4 (`@tailwindcss/vite`) сканирует шаблоны и включает в бандл только
реально использованные утилиты — ручной PurgeCSS не нужен. Конфиг — в CSS через
`@theme` (файла `tailwind.config.js` нет).

- Избегайте раздутого глобального CSS; используйте готовые компонентные классы
  (`.container-page`, `.section`, `.btn`, `.card`, `.eyebrow` и т.д.).
- Не тащите тяжёлые CSS-фреймворки поверх Tailwind.

## 5. Как шаблон помогает Core Web Vitals

- **LCP:** статический HTML отдаётся мгновенно (нет клиентского рендера), герой
  можно грузить с `fetchpriority="high"` + preload. Минимум JS не конкурирует за
  главный поток.
- **INP:** JS почти нет; острова ленивые (`client:visible`). Нет тяжёлых
  обработчиков — реакция на клики быстрая. Аналитика (`data-goal`) — один
  делегированный обработчик, обёрнутый в try/catch.
- **CLS:** задавайте `width`/`height` картинкам; `<Image>` делает это сам.
  Есть обработка `prefers-reduced-motion` в `global.css` — анимации не мешают.

## 7. Бюджет первой загрузки: проверять замером

Lighthouse показывает итог, но не отвечает на вопрос «что именно утекло». А
утекает регулярно: атрибут `loading="lazy"` **не гарантирует**, что картинка
ниже сгиба не загрузится (гонка с раскладкой — см.
[recipes/images-assets.md](recipes/images-assets.md#когда-loadinglazy-не-спасает)),
а отложенная догрузка по `window.load` стартует через доли секунды после
старта и качает своё вне зависимости от того, дойдёт ли посетитель.

Замер занимает полминуты. Открыть прод-сборку (`npm run preview`), **не
скроллить**, выполнить в консоли:

```js
// Сколько весит страница, если посетитель посмотрел первый экран и ушёл
(() => {
  const res = performance.getEntriesByType('resource');
  const kb = (a) => Math.round(a.reduce((s, r) => s + (r.encodedBodySize || 0), 0) / 1024);
  const by = (re) => res.filter((r) => re.test(r.name));
  return {
    scrollY,                                  // обязан быть 0
    totalKB: kb(res),
    imagesKB: kb(by(/\.(webp|avif|jpe?g|png|svg)/)),
    scriptsKB: kb(by(/\.js/)),
    // подставить префикс своей тяжёлой секции:
    heavySectionKB: kb(by(/frame-|\/seq\//)),
    loadEventEnd: Math.round(performance.getEntriesByType('navigation')[0].loadEventEnd),
  };
})()
```

Важно: `transferSize` при повторном заходе равен нулю (кэш) и врёт —
считать по **`encodedBodySize`**, он отражает реальный вес полезной нагрузки
независимо от кэша.

Что считать нормой: у тяжёлой секции ниже сгиба на `scrollY = 0` должно быть
**0 КБ**. Пример из практики (боевой проект): до правки секция тянула 3597 КБ
секвенции + 123 КБ базовых кадров через 197 мс после `load`; после
гейтинга по «load И близость» — 0 КБ, LCP 579 → 280 мс.

Дальше — прокрутить к секции и убедиться, что ассеты пришли и успели
декодироваться до входа в неё (`seqReady`, отсутствие мигания). Полный
харнесс проверок для скролл-сцен: [qa/scroll-scene-qa.md](qa/scroll-scene-qa.md).

## 8. Канон скриптов и закадровых секций (уроки боевого проекта)

**Скрипты: бандл по умолчанию, `is:inline` — только для verbatim.** Обычный
`<script>` в Astro-компоненте типизируется, бандлится в кэшируемый чанк и не
раздувает каждый HTML-документ. `is:inline` оправдан ровно там, где нужен
дословный вывод в документ: счётчик Метрики, JSON-LD, reveal-гейт и
cv-предохранитель в `<head>` (они обязаны отработать до отрисовки). На
боевом проекте перевод скриптов из inline в бандл дал −5% веса документа и
заодно вскрыл 46 ошибок типов, которые inline-скрипты прятали. Помни граблю
№30 (`docs/recipes/gotchas.md`): тело `is:inline` нельзя оборачивать в
`` {`…`} ``.

**Закадровые секции: `content-visibility` через `.cv-auto`.** На длинных
страницах браузер считает стиль и layout всего документа до первого кадра.
Класс `.cv-auto` (см. `global.css`) включает `content-visibility: auto` +
`contain-intrinsic-size: auto var(--cv-h)`. Правила: высоту `--cv-h` мерить
в devtools (враньё = дёргающийся скроллбар); секции с пином ScrollTrigger не
помечать; предохранитель для якорей `:root.cv-off` уже стоит в
`BaseLayout.astro`. На боевом проекте это срезало ~600 мс style/layout при CPU 4x.

**Один eager LCP-кандидат на страницу.** Ровно одна картинка первого экрана
грузится с `loading="eager"` + `fetchpriority="high"`; всё остальное — lazy.
Два «eager» конкурируют за канал и оба проигрывают.

**Prefetch — `hover`, не `viewport`.** В `astro.config.mjs` стоит
`prefetchAll: true` + `defaultStrategy: 'hover'`: стратегия `viewport` на
страницах с плотной навигацией (каталог) скачивает десятки соседних страниц
впустую и греет мобильный канал.

**Тяжёлую библиотеку — через `loadOnce`/`whenNear` из `src/lib/lazy-module.ts`.**
Не голый `import()` в топ-левел скрипте секции: `loadOnce` мемоизирует
динамический импорт (повторный ре-маунт секции не гоняет загрузку заново),
`whenNear` откладывает её до подхода посетителя к секции на N% экрана вперёд.
Пример использования (GSAP + ScrollTrigger) — в doc-comment самого файла.

**Ленивые виджеты нельзя вешать на один только `astro:page-load`.** Самая
дорогая грабля этого раздела: разбор 24.08.2026 на боевом проекте-доноре. Карта
инициализировалась строкой

```js
document.addEventListener('astro:page-load', initMap);   // ← и всё
```

а ClientRouter диспатчит это событие на **первичной** загрузке по
`window.load` — см. `astro/dist/transitions/router.js`,
`addEventListener("load", onPageLoad)`. То есть после всех картинок, шрифтов
и сторонних скриптов. Последствия наблюдались на боевом сайте месяцами:

- виджет появлялся через несколько секунд после того, как секция уже в кадре;
- `IntersectionObserver`, который должен был начать загрузку, до `window.load`
  **не существовал**, поэтому и сейф-таймер внутри него не срабатывал;
- если человек на медленной сети успевал **проскроллить мимо** секции до
  `window.load`, наблюдатель создавался на уже уехавшем элементе. IO отдаёт
  стартовый колбэк с `isIntersecting: false` и больше не срабатывает никогда —
  виджет не грузился до конца сессии. Симптом «карты иногда просто нет».

Канон (образец — `src/components/ui/YandexMap.astro`):

```js
if (document.readyState === 'loading')
  document.addEventListener('DOMContentLoaded', init, { once: true });
else init();                                    // скрипт уже после парсинга
document.addEventListener('astro:page-load', init);   // SPA-переходы
```

плюс три обязательные детали:

1. **Гард от двойного запуска на самом узле** (`el.dataset.booted`), а не в
   замыкании: после SPA-свопа узел новый — значит возврат на страницу честно
   переинициализирует виджет, а двойной вызов в рамках одной страницы гасится.
2. **Проверка «секция уже за спиной»** перед созданием наблюдателя:
   `if (el.getBoundingClientRect().bottom < 0) startLoading();`. Иначе
   восстановление прокрутки после свопа, переход по якорю или перезагрузка на
   середине страницы оставляют виджет мёртвым. Само восстановление позиции
   живёт в `src/lib/scroll-restore.ts` (подключено в `BaseLayout.astro`) и
   работает по ориентиру, а не по пикселю — оно возвращает человека вглубь
   страницы раньше, чем виджеты успевают загрузиться, поэтому эта проверка
   обязательна. Разбор — [recipes/scroll-pitfalls.md](recipes/scroll-pitfalls.md).
3. **Уборка на `astro:before-swap`**: `observer.disconnect()`,
   `resizeObserver.disconnect()`, `instance.destroy()` — иначе инстанс висит на
   оторванном узле и течёт при каждом возврате.

Регрессия закрыта тестом `src/components/ui/__tests__/yandex-map-boot.test.ts`:
он гоняет настоящий inline-скрипт компонента в стабе окружения и падает, если
запуск вернут на один `astro:page-load`.

**Ключи сторонних API проверять на СБОРКЕ, а не молча деградировать.** Тот же
разбор: `PUBLIC_MAPS_API_KEY` при переносе из эталона-каталога переименовали (там
`PUBLIC_YANDEX_MAPS_API_KEY`), значение не доехало, и карта полгода отдавала
фолбэк-iframe — без фирменной метки, с обесцвечиванием поверх интерфейса
Яндекса. Никакой ошибки при этом не было: фолбэк на то и фолбэк. Поэтому во
фронтматтере стоит `console.warn` при пустом ключе — предупреждение попадает в
лог сборки Freim Deploy. Сборка статическая: переменная нужна в окружении
**билда**, а не рантайма.

## 9. Честный `sizes`: снимать замером, а не «на глаз»

`sizes` на адаптивной картинке — это обещание браузеру, какой слот займёт
картинка в разметке. Обещание, взятое с потолка (типичное
`"(min-width: 900px) 55vw, 100vw"`) почти всегда завышено: реальная карточка
где-то упирается в `max-width` и дальше не растёт, а браузер, доверяя
`sizes`, честно тянет ступень `srcset` под завышенный слот — лишние
килобайты на каждой загрузке страницы. Lighthouse такое ловит как «Improve
image delivery», но не говорит, какой именно блок виноват — виноватого
находит только замер.

**Метод.**

1. На живой странице (прод-сборка, не dev) снять `getBoundingClientRect()`
   реального слота на характерном наборе брейкпоинтов — например 390 / 768 /
   950 / 1024 / 1460 / 1920. Записать числа рядом с константой `sizes` в
   коде (doc-комментарий), а не только в этом файле — иначе следующая
   правка вёрстки разойдётся с `sizes` незаметно.
2. Замерять **в чистом контексте браузера** — новая вкладка или окно
   инкогнито. Обычная вкладка может уже держать в памяти крупную ступень
   `srcset` из предыдущей загрузки и переиспользовать её вместо честного
   решения по актуальному `sizes` — замер покажет ложно хороший результат.
3. Добавить в набор ширин ступень **под ретину** относительно измеренного
   максимума, а не полагаться на ближайшую из дефолтного ряда: слот 540px
   на DPR 2 требует физических 1080px, и если в `widths` есть только 960 и
   1440 — браузер перепрыгивает сразу на 1440, хотя хватило бы 1120.
4. Прогнать по всем `<img>` страницы консольный снимок «обещано vs
   реально»:

```js
// На отрисованной странице — на каждый <img> сравнить фактический слот
// (sizes) с фактически отданным ресурсом (naturalWidth растянутого файла)
[...document.images].map((img) => {
  const rect = img.getBoundingClientRect();
  const ratio = img.naturalWidth / (rect.width * devicePixelRatio);
  return { src: img.currentSrc.split('/').pop(), slotPx: Math.round(rect.width), naturalW: img.naturalWidth, ratio: +ratio.toFixed(2) };
});
```

**Пороги.** `ratio` (реально отданное / нужное под текущий DPR) до **1.05×**
— норма, ничего чинить не надо. **1.26–1.4×** — это дискретность ступеней
`widths` (соседних вариантов вроде 960/1200 не бывает бесконечно много), а
