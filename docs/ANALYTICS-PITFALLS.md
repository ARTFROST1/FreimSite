# Аналитика и формы: грабли, на которые мы уже наступили

> Каждая ошибка здесь стоила боевому проекту денег или данных. Все они
> **уже исправлены в шаблоне** — этот документ нужен, чтобы их не вернули
> обратно «упрощая» код и чтобы узнавать симптомы, когда что-то похожее
> всплывёт на новом проекте.
>
> Источник: разбор инцидента на боевом проекте-доноре, 21.08.2026. Реклама шла,
> заявки терялись, директолог видела нули в целях.

## №1. Цель + немедленный переход = потерянная конверсия

**Симптом.** В базе заявки есть, в чате менеджеров есть, а в Метрике по цели
«отправка заявки» — ноль. Причём другие цели (клики по кнопкам) считаются
нормально.

**Причина.** Так писать нельзя:

```js
reachGoal('lead_submit');
window.location.assign('/thanks/');   // ← страница выгружается прямо сейчас
```

`reachGoal` асинхронный. Браузер начинает уходить на новую страницу и
выбрасывает недоотправленный запрос. Цель умирает вместе со страницей.

**Как правильно** (так и сделано в `src/lib/lead-form.ts`):

```js
let redirected = false;
const go = () => { if (redirected) return; redirected = true; window.location.assign(url); };
reachGoal('lead_submit', { source }, go);  // 5-й аргумент — callback Метрики
window.setTimeout(go, 1200);               // страховка: не держим клиента
```

Callback вызывается после фактической отправки. Таймаут обязателен: если
Метрика заблокирована или молчит, посетитель не должен зависнуть.

**Правило.** Везде, где за целью следует переход, закрытие вкладки или
`form.submit()`, цель отправляется с callback и страховочным таймаутом.

## №2. Гейт согласия на счётчике съедает 80–90% данных

**Симптом.** Метрика показывает в разы меньше визитов, чем логи сервера.
Директолог жалуется, что «не видит достижений», Вебвизор почти пуст, у
поддержки Яндекса вопросы к «модифицированному коду счётчика», а
`_ym_debug=1` не включается.

**Замеренная цена.** За сутки: **141 посетитель по access-логам Caddy против
19 визитов в Метрике**. Мы не видели ~85% людей — по ним не было ни целей,
ни записей Вебвизора, ни данных для обучения ставок в Директе. При платной
рекламе это прямые потери.

**Причина.** Счётчик грузится только после клика «Принять» в cookie-баннере.
Большинство людей баннер игнорирует и уходит смотреть сайт.

**Как в шаблоне.** `PUBLIC_METRIKA_CONSENT_GATE` по умолчанию **выключен**:
счётчик грузится сразу, баннер остаётся информационным. Включение (`=1`) —
осознанное решение заказчика или его юриста, принятое с этими цифрами на
руках, а не молчаливое значение по умолчанию.

**Проверка на новом проекте.** Сравнить уникальных посетителей по логам
веб-сервера с визитами в Метрике за те же сутки. Расхождение больше чем в
полтора раза — идти смотреть, что придерживает счётчик.

## №3. Цель «за страницу» вместо «за визит» в SPA

**Симптом.** Достижений цели больше, чем визитов. У нас было **27
достижений `deep_scroll` на 19 визитов**, а в отдельные часы — 5 достижений
на один визит.

**Причина.** Флаг «уже сработало» жил в переменной модуля и сбрасывался на
каждой SPA-навигации (`astro:page-load`). Посетитель листает каталог — цель
считается заново на каждой карточке.

**Как правильно.** Флаг в `sessionStorage`, а не в памяти:

```js
try { fired = sessionStorage.getItem('app_deep_scroll') === '1'; } catch (e) {}
```

**Правило.** Для поведенческих целей сначала решить, что именно считаем:
действие **за визит** (скролл, вовлечённость, время на сайте) или **за
страницу** (просмотр товара). Первое — `sessionStorage`, второе — переменная
в модуле. Цель, которая срабатывает по нескольку раз за визит, бесполезна
для обучения ставок: она перестаёт отличать заинтересованного человека от
случайного.

## №4. Ловушка для ботов не должна удалять заявку

**Симптом.** Клиент отправил заявку, увидел страницу «Спасибо» — заявки
нигде нет. В логах сервера её запрос есть, и ответ **201 «принято»**.

**Причина.** Классический honeypot: скрытое поле, которое человек не видит,
а бот заполняет. Поле называлось `company` и имело подпись «Компания» — и
**автозаполнение браузера подставляло в него организацию у живых людей**.
Сервер считал их ботами и молча выбрасывал заявку, отвечая фальшивым
успехом. `autocomplete="off"` браузеры при автозаполнении игнорируют, а вот
на семантику имени и подписи ориентируются.

**Как правильно.** Ловушка нужна (боты действительно шлют мусор), но она
обязана быть устроена так, чтобы ложное срабатывание не стоило клиента:

1. **Имя поля бессмысленное** — `hp_token`, без подписи, без placeholder.
   Никаких `name`, `email`, `phone`, `company`, `address`, `website`:
   именно по ним автозаполнение узнаёт поле.
2. **Срабатывание не удаляет заявку**, а откладывает её в карантин:
   отдельная папка на диске плюс событие `quarantined` в общем журнале.
   Менеджерам она не приходит, черновик не создаётся, отложенная отправка
   её не разошлёт.
3. **Ответ клиенту остаётся 201** — бот не должен понять, что его отсекли.
4. **Карантин чистится по TTL** (в шаблоне 14 дней): достаточно, чтобы
   заметить ошибку и достать номер живого человека, и не превращается в
   вечное хранилище чужих телефонов.
5. **Счётчик карантина виден в `/api/health`** — всплеск означает «идём
   смотреть глазами, не ловим ли людей».

Ключевая мысль: ловушка переводит подозрительную заявку в режим ручного
разбора, а не в небытие. Спам-запись стоит секунды внимания, потерянный
клиент — денег и репутации.

Референс-реализация: `quarantineLead()` в `src/lib/lead-server/leads.ts`,
уборка — `sweepQuarantine()` в `server/lead-flusher.mjs`, тесты —
`src/lib/__tests__/lead-quarantine.test.ts`.

**Чего делать нельзя ни при каких условиях:** отвечать «успех», ничего не
сохранив. Это делает потерю невидимой для всех сразу — и для клиента, и
для менеджера, и для разработчика.

## №5. Цель на навигационной ссылке

**Симптом.** Директолог: «цель „клик по CTA“ срабатывает на кнопку
„Каталог“». Цель есть, но по ней невозможно судить о намерении.

**Причина.** `data-goal="cta_click"` поставили на ссылку «смотреть все
работы» и на кнопку «весь каталог» на странице «Спасибо». Обе ведут в
каталог, а не к форме.

**Правило.** Цель `cta_click` — только на элементах, которые ведут к форме
заявки. Проверка одной строкой в консоли на готовом сайте:

```js
[...document.querySelectorAll('[data-goal="cta_click"]')]
  .every(a => /#calculation|#lead|#form/.test(a.getAttribute('href') || ''))
```

Должно вернуть `true`. И обратная проверка — что метки нет на навигации:

```js
[...document.querySelectorAll('a[href*="/catalog/"]')]
  .filter(a => a.dataset.goal === 'cta_click').length   // должно быть 0
```

## №6. Цели нельзя проверить автоматизированным браузером

**Симптом.** Прогнали форму через Playwright / agent-browser / CDP, всё
работает, а в отчётах Метрики по этому визиту — ноль целей.

**Причина.** Метрика засчитывает визит (он даже помечен «People»), но
достижения целей из автоматизированного браузера отбрасывает. Проверено
разбивкой по часам: тестовый визит дал 1 визит и 0 целей, включая скролл,
тогда как у живых посетителей в те же сутки цели считались.

**Как проверять на самом деле:**

1. **Косвенно, роботом** — что цепочка вызывается: перехватить `window.ym`
   и убедиться, что `reachGoal` дошёл с нужными параметрами; посмотреть в
   `performance.getEntriesByType('resource')` запросы к `mc.yandex.ru`;
   проверить, что заявка легла в базу и ушла менеджерам.
2. **Прямо, руками** — отправить заявку с обычного телефона и посмотреть
   достижение в отчёте. Другого способа подтвердить цель нет.

## №7. `defer: true` без ручного первого хита

Официальная SPA-схема Метрики: `defer: true` **отключает автоматическую
отправку первого просмотра**, и все просмотры, включая первый, шлёт ваш
код на каждом `astro:page-load`.

Две половины связаны намертво:

- `defer` без ручного первого хита → потерян первый просмотр каждого визита;
- ручной хит без `defer` → первый просмотр считается дважды.

В шаблоне это `YandexMetrika.astro` (init) + `AnalyticsRouterHit.astro`
(хиты). Менять одно без другого нельзя — в обоих файлах об этом написано.

## №8. Сервис картинок Astro не апскейлит — OG-мета может врать о размере

**Симптом.** Превью ссылки в мессенджере или соцсети не показывается либо
показывается обрезанным/размытым, хотя `og:image` в разметке указан
правильно, а сама картинка открывается по ссылке без проблем. Заметил живой
человек, переслав ссылку в мессенджере, — автоматических алертов на это нет.

**Причина.** Мета-теги `og:image:width`/`og:image:height` часто прописывают
константой (например, 1200×630 — стандартный формат превью), а
`astro:assets` **не увеличивает** оригинал сверх его реального размера: если
исходник меньше заявленных констант, отданный файл будет мельче, чем
обещает мета. Соцсети и мессенджеры сверяют заявленные в мете размеры с
фактическими у самого файла и при расхождении либо ужимают/обрезают
превью, либо не показывают его вовсе. На боевом каталоге это задело больше
сотни карточек товаров, где исходники были меньше формата OG.

**Правило.** OG-размеры в мете — не константа «по стандарту», а **факт**:
брать их из реальных выходных данных генератора превью (ширина/высота
файла, который действительно отдаётся по `og:image`), а не из значения,
которое кажется правильным форматом. При массовой генерации OG-картинок
(каталог, блог) — проверять на выборке, что declared-размеры совпадают с
фактическими у сгенерированного файла, а не только у мастер-шаблона.

## №9. Regex-условие цели ловит цели-соседи по префиксу

**Симптом.** В отчёте по цели с более узким условием (например,
`ym_prefix30`, «досмотрел 30% страницы») внезапно попадают события с других,
похожих по имени целей той же лестницы (`ym_prefix300` и подобные) —
воронка «лестницы» вовлечённости считает нечестно, соседние ступени
задваиваются.

**Причина.** Условие цели в Метрике задано регулярным выражением
(`url`/`event` содержит подстроку), а не точным совпадением. Регулярка
`ym_prefix30` матчит и `ym_prefix30`, и `ym_prefix300`, и вообще любую
строку с этой подстрокой где угодно — это находка регэкспа, а не намерение
того, кто заводил цель.

**Правило.** Для лестницы связанных по имени целей (набор с общим префиксом
и разными суффиксами-числами) условие всегда — точное совпадение, а не
regex-подстрока. Regex в условиях целей оставлять только там, где
действительно нужен произвольный паттерн (например, диапазон URL), и
проверять его на соседних именах перед сохранением.

## №10. Цель на странице «Спасибо» считает прямые заходы

**Симптом.** Директолог радуется конверсии, а заявок нет. Или наоборот:
«цель срабатывает, а заполнения полей не видно» — потому что заполнения
и не было.

**Боевой случай (25.08.2026).** Страницу `/thanks/` открыли по прямой
ссылке 33 раза, проверяя, ловится ли цель. Метрика записала **32
«конверсии» при НУЛЕ отправленных заявок**: ни одного `lead_contact`, ни
одного `lead_submit`. За неделю до этого — та же картина в меньшем
масштабе.

**Причина.** Цель висит на показе страницы. Страница доступна по адресу.
Значит цель накручивается открытием адреса: закладкой, возвратом по
истории, повторной загрузкой, чужой ссылкой в переписке.

**Опасность не в отчётах, а в деньгах.** Такая цель в 6–15 раз «дешевле»
настоящей заявки. Если на ней учится кампания в Директе, алгоритм честно
наберёт вам тех, кто открывает адреса, а не оставляет телефон.

**Как правильно.** Метку в адрес ставит ТОЛЬКО движок формы после успешной
отправки, и цель засчитывается только при её наличии:

```js
var from = new URLSearchParams(location.search).get('from');
if (!from) return;                       // прямой заход — не конверсия
window.trackConversion('lead_thankyou', { source: from });
```

Метка заодно размечает источник (`calc` / `popup` / `ctor`) — видно, какая
форма приносит заявки.

**Проверка.** Открыть страницу «Спасибо» по прямой ссылке без параметра —
достижения не должно появиться.

## №11. Жёсткий переход после формы рвёт запись Вебвизора

**Симптом.** В записи визита видно, как человек листает сайт и заполняет
форму, потом запись **обрывается**, а страница «Спасибо» открывается
пустой: фон и шапка есть, контента нет. Со стороны выглядит как «Вебвизор
сломан» или «счётчик установлен неправильно».

**Причина.** `window.location.assign()` уничтожает документ целиком.
Вебвизор копит DOM в буфере и отправляет порциями — всё, что не успело
уйти, пропадает вместе со страницей. Отсюда обрыв ровно на отправке формы.
Дальше на странице «Спасибо» начинается новая запись, но человек проводит
там секунды, и снимок не успевает отправиться.

Важно: теряется ТОЛЬКО запись. Заявка, цель и просмотр страницы доезжают —
поэтому по цифрам всё выглядит нормально, и найти причину тяжело.

**Как правильно.** Переходить кликом по обычной ссылке — тем же путём, что
любая другая ссылка сайта. `ClientRouter` перехватит клик и сделает
клиентскую навигацию: документ живёт дальше, запись не рвётся, просмотр
считает ручной хит на `astro:page-load`.

Именно клик, а не `navigate()` из `astro:transitions/client`: один путь со
всеми остальными переходами, без отдельной ветки поведения и без импорта
виртуального модуля Astro в общую библиотеку. Готовая реализация —
`navigateToThanks()` в `src/lib/lead-form.ts`, тесты —
`lead-form-navigate.test.ts`.

**Деградация встроена:** нет роутера — браузер уйдёт по `href` сам.
Страховка на 400 мс — если клик не увели ни роутер, ни браузер.

**Правило шире одной формы:** на сайте не должно остаться НИ ОДНОГО
жёсткого перехода. Проверка — `grep -rn "location.assign\|location.href ="`.

## №12. Автоцели Метрики нельзя использовать как источник правды

**Боевые цифры за два месяца на одном сайте:**

| Цель | Срабатываний |
| --- | --- |
| Автоцель «отправка формы» | **237** |
| Реальных заявок (своя цель) | **17** |
| Автоцель «заполнил контактные данные» | 2 |
| Автоцель «отправил контактные данные» | 0 |

Завышение в **14 раз** у одной и почти полное молчание у двух других. На
одной и той же отправке формы одна автоцель срабатывала, вторая нет.

**Причина.** Автоцели — эвристика: Яндекс УГАДЫВАЕТ по DOM, что считать
формой и что контактными данными. Эвристика не публикуется и меняется.

**Как правильно.** Свои цели срабатывают в конкретной строке своего кода в
конкретный момент, и каждую заявку видно ещё в двух местах: в журнале на
диске и в логах ботов. Три источника сходятся — вот это правда.

Автоцели стоит отключить: они засоряют список целей похожими названиями и
регулярно вводят в заблуждение и заказчика, и подрядчика по рекламе.

## №13. «Конверсия 100%» в отчёте — это применённый сегмент

**Симптом.** Заказчик открывает отчёт и видит конверсию 100%. Паника: цель
срабатывает на всех визитах подряд.

**Причина.** В отчёте применён сегмент «визиты, где достигнута цель». В
такой выборке остаются только целевые визиты, и Метрика честно считает:
76 целевых из 76 всего = 100%.

**Как распознать мгновенно.** Посмотреть на график: линия конверсии
скачет строго между 0% и 100%, промежуточных значений нет. Настоящая
конверсия так не выглядит — она колеблется около своих 3–5%.

**Вторая половина той же путаницы.** В таблицах Метрики серые проценты под
числами — это **доля от итога**, а не конверсия. Под строкой «Итого»
всегда стоит 100%, потому что это 100% самой себя. Конверсия — в отдельной
колонке «Конверсия».

## №14. Поддержка Метрики называет «модифицированным» любой SPA-счётчик

**Симптом.** Поддержка отвечает: «установлен модифицированный код счётчика,
из-за этого Вебвизор может работать некорректно, переустановите по
инструкции». Подрядчик по рекламе требует переустановки.

**Причина.** Проверка сравнивает текст сниппета с эталонным и не запускает
сайт. А официальная инструкция Метрики для SPA требует добавить
`defer: true`, которого в эталонном сниппете нет. То есть **любой
правильно собранный SPA-сайт всегда получит вердикт «модифицированный»**.

**Переустановка сделает хуже.** В стандартном сниппете нет `defer`, значит
счётчик начнёт сам отправлять первый просмотр — а ручной хит отправит его
же второй раз. Получите **удвоение первого просмотра на каждом визите**.

**Чем ответить — фактами, а не спором.** Открыть сайт с `?_ym_debug=1` и
показать вывод консоли: сколько просмотров ушло, с какими адресами и
реферерами. Это отчёт самого счётчика Яндекса:

```
PageView. Counter NNN. URL: https://site.ru/         Referrer:
PageView. Counter NNN. URL: https://site.ru/katalog/ Referrer: https://site.ru/
Reach goal. Counter: NNN. Goal id: lead_submit. Params: {source: "calc"}
```

Три страницы — три просмотра, цепочка переходов верная, дублей нет.

## №15. `_ym_debug` живёт в куке, а не в адресе

**Симптом.** «При переходе между страницами режим отладки сбрасывается».

**На самом деле не сбрасывается.** Метрика запоминает режим в куке
`_ym_debug`. Параметр `?_ym_debug=1` нужен ОДИН раз, дальше отладка живёт
до закрытия браузера. Проверено: открыть с параметром, уйти на другую
страницу полной перезагрузкой без параметра — вывод продолжается.

**Что пропадает на самом деле — сам вывод в консоли.** Chrome по умолчанию
очищает консоль при каждой перезагрузке страницы. Лечится галочкой
**Preserve log** в настройках DevTools.

Косвенная польза от №11: когда на сайте не осталось жёстких переходов,
консоль не очищается при обычной работе с сайтом вообще.

## №16. CSP и `X-Frame-Options` ломают карты кликов и Вебвизор

**Симптом.** Карта кликов, карта скроллинга и аналитика форм показывают
пустоту. В консоли: `Framing '...' violates the following Content Security
Policy directive: "frame-ancestors ..."`.

**Причина.** Эти отчёты открывают ЖИВОЙ сайт во фрейме внутри интерфейса
Метрики. Blanket `X-Frame-Options: DENY` режет фрейм молча.

**Как правильно.** Разрешить фрейминг доменам Метрики через
`Content-Security-Policy: frame-ancestors`. Список — дословно из справки
Яндекса «Установка счётчика на сайт с CSP», включая региональные зеркала
(`metrika.yandex.*`, `metrica.yandex.*`, `metr.yandex.*`,
`analytics.yandex.*`).

**`X-Frame-Options` обязан быть СНЯТ**, а не дополнен: браузеры дают ему
приоритет над `frame-ancestors`, и оставленный `DENY` превратит CSP в
no-op.

**Чего делать нельзя:** снимать защиту с админок и панелей. Там сессия
оператора — это ровно та мишень, ради которой кликджекинг существует.

В Freim Deploy это уже сделано на уровне платформы: клиентские сайты
получают домены Метрики автоматически, системные хосты сохраняют
blanket `DENY`.
