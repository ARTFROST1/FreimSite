# AGENT-PLAYBOOK.md — сборка сайта по HTML-прототипу

> **Кому.** ИИ-агенту (или разработчику), который получил на руки: (а) этот
> стартер, (б) HTML-прототип страницы/страниц будущего сайта, (в) бриф клиента.
> Задача — превратить прототип в сайт на этом шаблоне так, чтобы он выглядел
> как прототип **и** был полностью редактируем через наш CMS-портал.
>
> **Это входной документ проекта.** Прикрепляется к каждому новому сайту.
> Читается целиком **до первой правки кода**. Остальные документы читаются
> по ссылкам из него, когда до них доходит очередь.

**Обязательное чтение перед стартом (в этом порядке):**

1. этот файл целиком;
2. [`docs/CMS-BUILDING.md`](CMS-BUILDING.md) целиком — конвенция `data-cms`
   и цепочка «схема → контент → коллекция → контракт → разметка → тест».
   Без неё сайт соберётся, но клиент не сможет его редактировать.

Остальное — по мере необходимости: [`GUIDE.md`](GUIDE.md) (принципы
конверсии), [`ARCHITECTURE.md`](ARCHITECTURE.md) (карта файлов),
[`IMAGES.md`](IMAGES.md), [`SEO.md`](SEO.md), [`PERFORMANCE.md`](PERFORMANCE.md),
[`recipes/`](recipes/README.md) (боевые решения), [`recipes/gotchas.md`](recipes/gotchas.md) (грабли), [`recipes/anchor-navigation.md`](recipes/anchor-navigation.md) (якорная навигация — канон, читать перед любой правкой прокрутки).

**Как устроена документация.** У каждой темы один документ-владелец, полная
карта — в [README](../README.ru.md#документация). Этот playbook
владеет **процессом**: последовательностью работ, решениями «что во что
превратить» и чек-листами. Справочная глубина живёт у профильных документов —
здесь на неё даются ссылки, а не пересказ. Расходятся — прав профильный.

## 0. Десять инвариантов — нарушать нельзя

Если правило из этого списка конфликтует с «красиво/быстро/проще» — побеждает
правило. Каждое куплено болью на боевом проекте.

| # | Инвариант | Почему |
|---|---|---|
| 1 | **Ни одна видимая клиенту строка не живёт в `.astro`/`.ts`/`.tsx`.** Только `src/content/**/*.json` (или `.md`/`.mdx` для блога и товаров). | Никакая CMS не умеет писать TypeScript. Строка в компоненте = строка, которую клиент никогда не поправит. |
| 2 | **Каждое текстовое поле имеет `data-cms` в разметке.** Формат `collection:itemId:field`, ровно два двоеточия. | Иначе поле правится только формой, но не кликом по превью — половина ценности портала теряется. |
| 3 | **`data-cms` ставится на элемент, чей `textContent` РАВЕН значению поля целиком.** Пунктуация, иконки, вложенные теги — снаружи. | Оверлей делает `el.textContent = value`. Всё лишнее внутри стирается первой же правкой. |
| 4 | **Каждое поле схемы имеет `.describe('подпись по-русски')` и лимит длины** через `text(MAX.x, '…')`. | `.describe()` — единственный источник подписей формы портала. `MAX` → `maxLength` в контракте, который портал валидирует на сохранении. |
| 5 | **Новая коллекция регистрируется в `COLLECTIONS`** (`scripts/generate-content-schema.ts`), `content.schema.json` перегенерируется и коммитится. | Это allowlist. Не зарегистрировал — коллекция невидима для портала, хотя на сайте работает. |
| 6 | **`id` элемента массива и `singletonKey` — навсегда.** Добавлять новые можно, менять и переиспользовать старые — нет. | `id` — это связь «карточка в CMS ↔ блок на сайте». Смена рвёт уже сохранённые правки клиента. |
| 7 | **Что влияет на `href`/`tel:`/`mailto:`/JSON-LD — остаётся в `src/config/`,** в контент выносится только отображаемая копия. | Плохая правка структурных данных ломает выдачу или превращает рабочую ссылку в нерабочую. |
| 8 | **Цвета, шрифты, отступы — только через токены `@theme`** в `src/styles/global.css`. Хардкод hex в разметке запрещён. | Ребрендинг = смена 6 значений, а не обход 40 файлов. |
| 9 | **По умолчанию 0 KB JS.** React-остров — только там, где без него нельзя (формы с валидацией, лайтбокс). | Скорость — это конверсия и ранжирование одновременно. |
| 10 | **`npm test` (сборка + тесты) зелёный перед каждым коммитом.** | Rot-guard `annotations.test.ts` читает `dist/*.html` — он и есть защита от «рефакторинг молча снёс `data-cms`». |

## 1. Фаза 0 — приёмка входных данных

Прежде чем открывать редактор, соберите и зафиксируйте:

| Что | Обязательно | Если нет |
|---|---|---|
| HTML-прототип (все страницы) | да | без него нечего разбирать — стоп |
| Реквизиты бизнеса: название, юрлицо, телефон, email, адрес, координаты | да | ставим заглушки из `config/site.ts`, заводим TODO-список вопросов клиенту |
| Реальные фото | желательно | `public/images/placeholder.svg` + явный пункт «заменить фото» в приёмке |
| Реальные отзывы и рейтинг | — | **`rating.count: 0`** (блок скрывается). Выдуманные отзывы — санкции поисковиков, запрещено |
| Домен | да (до деплоя) | пишем реальный сразу, как узнали: `SITE_URL` + `SITE.url` + `robots.txt` |
| Тексты (копирайт) | нет | пишем сами по правилам `GUIDE.md` §B2 шаг 4, помечаем как черновик |

**Результат фазы:** список открытых вопросов клиенту. Он не блокирует работу —
всё, что можно, делаем на заглушках, но заглушка обязана быть заметной (не
«Lorem ipsum» вперемешку с реальным текстом).

## 2. Фаза 1 — аудит прототипа и карта разбора

Главный артефакт всего проекта. Не пропускать: без него декомпозиция
получается «на глаз», и половина блоков оказывается нередактируемой.

### 2.1. Инвентаризация

Пройдите прототип сверху вниз и выпишите:

- **Страницы** → какие маршруты нужны (`src/pages/`).
- **Блоки** на каждой странице, по порядку, с рабочим именем.
- **Дизайн-токены**: палитра (сколько реально уникальных цветов), шрифтовые
  семейства и начертания, радиусы, тени, ширина контейнера, вертикальный ритм
  секций, брейкпоинты.
- **Картинки**: сколько, где, какая роль (фон hero / карточка / галерея / иконка / логотип).
- **Интерактив**: что реально требует JS (аккордеон, слайдер, форма, лайтбокс,
  бургер, попап), а что — CSS.
- **Формы**: сколько, какие поля, куда должна уходить заявка.
- **Внешние виджеты**: карта, чат, календарь бронирования, счётчики.

### 2.2. Таблица разбора

Заведите файл `docs/build/prototype-map.md` (папку создайте) с таблицей:

| # | Блок прототипа | Компонент | Источник данных | `data-cms`-префикс | Новый код? |
|---|---|---|---|---|---|
| 1 | Первый экран с фоном | `HeroSection` | `hero` (синглтон) | `hero::*` | нет |
| 2 | 4 иконки-преимущества | `FeaturesSection` | `features` (массив) + `sections.features` | `features:<id>:*`, `sections::features.*` | нет |
| 3 | Карусель логотипов | `Marquee` | props | — | нет, но нужна коллекция, если клиент правит состав |
| 4 | Блок «Этапы работы» 1-2-3 | **новый** `ProcessSection`[^new-section-name] | новая коллекция `process` | `process:<id>:*` | **да, полный цикл из §5** |
| … | | | | | |

Эта таблица — контракт с самим собой. Пока она не заполнена целиком, код не
пишется.

[^new-section-name]: Имя условное — иллюстрирует цикл «завести новую
коллекционную секцию с нуля» (§5, §11). Не путать с готовым `StepsSection` в
каталоге компонентов (§9): он props-only (пропс `steps`, без своей
CMS-коллекции) — контракт, обратный этому примеру. См. doc-comment
`src/components/sections/StepsSection.astro`.

### 2.3. Как классифицировать блок — дерево решений

```
Блок из прототипа
   │
   ├─ Есть готовая секция с той же СМЫСЛОВОЙ ролью?  (см. каталог §9)
   │     ├─ да, и вёрстка близка          → берём как есть, правим только стили/токены
   │     └─ да, но вёрстка сильно другая  → берём КОНТРАКТ ДАННЫХ (схему+коллекцию),
   │                                        переписываем разметку внутри компонента
   │
   ├─ Это вариация существующей секции на другой странице?
   │     → тот же компонент + проп `cmsScope` (см. §5.5). НЕ копипаста файла.
   │
   └─ Ничего похожего нет
         → новый компонент + полный 7-шаговый цикл §5
```

**Правило замены разметки.** Если берём готовый компонент, но верстаем заново —
меняется только HTML внутри `---`-границы и классы. `getCollection`/`getEntry`,
имена полей и все `data-cms` **переносятся один в один**. Тогда `annotations.test.ts`
продолжает защищать блок бесплатно.

**Правило «одна секция — одна ответственность».** Если блок прототипа делает две
работы (например, «преимущества + форма»), это два компонента рядом, а не один.
Иначе клиент не сможет переставить их независимо, а вы не переиспользуете ни один.

## 3. Фаза 2 — дизайн-токены и pixel-perfect

### 3.1. Снять токены из прототипа

Откройте `src/styles/global.css`, блок `@theme` — это единственный источник
бренда. Заполните из прототипа:

```css
@theme {
  --color-paper:      /* фон страницы */
  --color-surface:    /* фон чередующихся секций, карточек */
  --color-ink:        /* основной текст */
  --color-muted:      /* вторичный текст */
  --color-line:       /* границы, разделители */
  --color-accent:     /* главный акцент: кнопки, ссылки */
  --color-accent-ink: /* текст НА акценте */

  --font-heading: 'Brand Sans', ui-sans-serif, system-ui, sans-serif;
  --font-body:    ui-sans-serif, system-ui, sans-serif;

  --container-max: 1200px;   /* ширина контента из прототипа */
  --radius-sm / md / lg / xl;
}
```

Токен `--color-accent` автоматически даёт утилиты `bg-accent`, `text-accent`,
`border-accent`. **В разметке — только они.** Увидели `bg-[#c2703d]` — это баг,
а не стиль.

Если в прототипе цветов больше, чем токенов, — сначала спросите себя, все ли они
осмысленны. Обычно 20 оттенков в макете сводятся к 7 токенам + прозрачности
(`bg-accent/10`). Добавляйте новый токен только под реальную семантическую роль.

### 3.2. Шрифты

Прототип почти наверняка подключает Google Fonts ссылкой. **Так в продакшен не
выкатываем** (скорость + 152-ФЗ). Порядок:

1. Скачать нужные начертания, subset latin+cyrillic, конвертировать в WOFF2.
2. Положить в `src/assets/fonts/`, НЕ в `public/` (кэш-заголовки —
   см. `src/assets/fonts/README.md` и `PERFORMANCE.md` §3).
3. Прописать `@font-face` в `global.css` относительным путём (образец — в шапке
   файла) и навести на него `--font-heading` / `--font-body`.
4. Добавить импорт `?url` + `<link rel="preload" as="font" …>` в
   `BaseLayout.astro` — оба должны указывать на один файл.

### 3.3. Порядок работ ради pixel-perfect

Опыт: «сверстать похоже, потом подгонять» стоит дороже, чем сделать по слоям.

1. **Токены** (§3.1) — до любой вёрстки. Тогда 80 % совпадения приходит само.
2. **Каркас страницы**: контейнер, вертикальный ритм секций (`.section`,
   `.container-page`), сетка. Проверить на десктопе и мобиле **пустыми блоками**,
   до контента.
3. **Блок за блоком**, сверху вниз. Каждый — до состояния «совпадает», прежде
   чем браться за следующий. Не набрасывать все десять и потом чинить.
4. **Мобильная версия — не в конце.** Основной трафик — телефоны. Проверяйте
   каждый блок в обеих раскладках сразу.
5. **Сверка**: скриншот прототипа и скриншот сборки рядом, при 100 % масштабе,
   на одной ширине вьюпорта. Смотреть в порядке: вертикальный ритм → размеры
   шрифтов → межбуквенное/межстрочное → цвета → радиусы/тени → состояния
   (hover/focus/active).

### 3.4. Что НЕ переносить из прототипа

- **Инлайновые стили и `<style>` в теле** — переводить в утилиты Tailwind или,
  если паттерн повторяется 3+ раза, в компонент-класс в `global.css` (там уже
  есть `.btn`, `.card`, `.eyebrow`, `.section`, `.container-page`, `.scroll-x`).
- **jQuery/бутстрап/любые библиотеки прототипа** — в шаблоне их нет и не будет.
  Аккордеон, бургер, слайдер — CSS или 15 строк ванильного `is:inline`-скрипта.
- **`<img>` с прямыми путями** — только через `<ContentImage>` (см. §6).
- **Хардкод текста** — он уезжает в JSON (см. §4).
- **Анимации на скролле** — в шаблоне уже есть система: атрибут `data-reveal`
  на элементе, задержка через `style="transition-delay: 70ms"`. Она
  SEO-безопасна (без JS и при `prefers-reduced-motion` контент просто виден).
  Рецепты сложнее — `docs/recipes/animations-motion.md`.

## 4. Фаза 3 — модель контента

Самая ответственная фаза. Ошибка здесь стоит переделки всего блока.

### 4.1. Классификатор: контент / конфиг / дизайн

Для **каждой** строки и каждого значения из прототипа ответьте, куда оно едет:

| Признак | Куда | Пример |
|---|---|---|
| Клиент захочет менять сам, влияет только на видимый текст | **`src/content/**/*.json`** (CMS) | заголовок, описание тарифа, вопрос FAQ, отображаемый телефон, адрес одной строкой |
| Клиент менять не должен; влияет на ссылку, структурные данные, маршрут | **`src/config/`** | `SITE.contact.phoneRaw` (для `tel:`), `SITE.address.*` (для JSON-LD), `href` пунктов меню, `PRIMARY_CTA.href` |
| Меняется раз в жизни, поломка = сломанная форма/доступность | **в коде** | тексты ошибок валидации, `aria-label`, строки 404/cookie-баннера |
| Юридический риск при правке | **в коде** | `src/config/legal.ts` (реквизиты, сроки, обработчики) + правовые страницы `privacy-policy.astro` / `terms.astro` (см. `docs/LEGAL.md`) |
| Это оформление, а не содержание | **токены/классы** | цвета, отступы, порядок колонок |

Пограничный случай, который встречается всегда, — **телефон**: отображаемая
строка это контент, сырое значение для `tel:` — конфиг. Готовая разметка для
такой пары (`data-fd-attr="href" data-fd-attr-template="tel:{value}"`) — в
`Header.astro`. Полный разбор, что именно остаётся в коде и почему, —
[`CONTENT.md` → «Что НЕ выносить в контент»](CONTENT.md).

### 4.2. Массив или синглтон

| Берём | Когда | Файл выглядит как |
|---|---|---|
| **массив** | число элементов задаёт клиент; порядок может меняться перетаскиванием | `[{ "id": "…", … }, …]` |
| **синглтон** | ровно один экземпляр, либо фиксированный набор именованных блоков, заданный вёрсткой | `{ "main": { … } }` |

Порядок массива = порядок в файле. Поля `order` **нет и не заводить**:
перетаскивание в портале переписывает массив.

Группируйте в один синглтон то, что редактор воспринимает как один экран
(«Тексты разделов» — `sections.json`, «Тексты страниц» — `pages.json`).
Адресация внутри — dot-путём: `sections::intro.title`, `pages::about.heading.subtitle`.

### 4.3. Именование

- `id` — осмысленный слаг (`basic`, `advantage-speed`, `slide-workshop`),
  не порядковый номер и не отображаемое значение.
- `singletonKey` — по конвенции `'main'` (историческое исключение: `rating`
  использует `'aggregate'`).
- Имена полей — на английском, короткие, повторяющие существующие
  (`title`, `subtitle`, `eyebrow`, `body`, `description`, `image`, `cta.label`,
  `cta.href`). Единообразие полей — это единообразие форм в портале.

### 4.4. Лимиты длины

В `src/config/schemas.ts` объявлен набор `MAX` (`slug`/`label`/`line`/
`sentence`/`paragraph`/`icon`/`path`) и хелпер `text(max, description)`.
**Каждое новое строковое поле объявляется только через него** — так нельзя
завести поле, забыв про лимит:

```ts
title: text(MAX.line, 'Заголовок карточки'),
```

Лимиты — это не цель, а потолок (примерно ×10 от самого длинного реального
текста). Они попадают в `content.schema.json` как `maxLength`, и портал
проверяет их при сохранении: это и защита вёрстки от 50-килобайтного
«заголовка», и ограничение размера возможной инъекции в текстовые приёмники.

Для массивов есть парный `MAX_ITEMS` в `scripts/generate-content-schema.ts` —
добавляя новую коллекцию-массив, добавьте туда её потолок.

## 5. Фаза 4 — реализация блока: цикл из 7 шагов

Это сжатая версия. **Полная, с примерами и разбором ошибок —
[`docs/CMS-BUILDING.md`](CMS-BUILDING.md), читать обязательно.**
Цикл выполняется целиком для **каждого** нового редактируемого блока.

```
1. Схема      src/config/schemas.ts        — Zod + .describe() + text(MAX.…)
2. Контент    src/content/**/*.json        — массив с id или синглтон
3. Коллекция  src/content.config.ts        — defineCollection + file()  → npx astro sync
4. Контракт   scripts/generate-content-schema.ts → COLLECTIONS (+ label, + MAX_ITEMS)
5. Разметка   компонент                    — data-cms на каждом текстовом поле
6. Рот-гвард  scripts/__tests__/annotations.test.ts → дополнить карты полей
7. Прогон     npx tsx scripts/generate-content-schema.ts && npx astro sync && npm test
```

### 5.1. Шаг 1 — схема

```ts
export const processSchema = z.object({
  id,
  number: text(MAX.label, 'Номер шага'),
  title: text(MAX.line, 'Заголовок шага'),
  description: text(MAX.sentence, 'Описание шага'),
});
export type ProcessStep = z.infer<typeof processSchema>;
```

Тип берётся из `z.infer` и импортируется в компонент — интерфейсы не дублируем.

### 5.2. Шаг 2 — контент

Файл кладётся по смыслу: `src/content/home/` (блоки главной),
`src/content/nav/` (сквозные шапка/футер/адрес), `src/content/pages/`
(тексты второстепенных страниц), `src/content/<page>/` (новая страница со
своим набором блоков).

**Тексты копируются из прототипа как есть.** Если переносите существующий блок
шаблона в JSON — видимый текст не должен измениться ни на символ.

### 5.3. Шаг 3+4 — коллекция и контракт

```ts
// src/content.config.ts
const process = defineCollection({ loader: file('src/content/home/process.json'), schema: processSchema });
export const collections = { /* … */ process };
```

```ts
// scripts/generate-content-schema.ts → COLLECTIONS
{ name: 'process', label: 'Этапы работы', schema: processSchema,
  filePath: 'src/content/home/process.json', kind: 'array' },
```

`label` по-русски — обязателен, его видит клиент в списке коллекций портала.
Для синглтона вместо `kind: 'array'` — `kind: 'singleton'` + `singletonKey: 'main'`.

После правки `content.config.ts` — **`npx astro sync`**, иначе типы коллекции не
появятся и сборка упадёт с `Argument of type "process" is not assignable to
parameter of type 'keyof DataEntryMap'`.

### 5.4. Шаг 5 — разметка

```astro
---
import { getCollection } from 'astro:content';
const PROCESS = (await getCollection('process')).map((e) => e.data);
---
{PROCESS.map((s) => (
  <div class="card p-6">
    <span class="eyebrow" data-cms={`process:${s.id}:number`}>{s.number}</span>
    <h3 class="mt-2 text-xl font-semibold" data-cms={`process:${s.id}:title`}>{s.title}</h3>
    <p class="mt-2 text-muted" data-cms={`process:${s.id}:description`}>{s.description}</p>
  </div>
))}
```

Правила разметки, каждое из которых уже стоило бага:

| Правило | Правильно | Неправильно |
|---|---|---|
| Атрибут на элементе, чей текст = значению | `<h3 data-cms="…">{title}</h3>` | `<h3 data-cms="…">{title} — {subtitle}</h3>` |
| Внутри ссылки/кнопки — `<span>`, не сам `<a>` | `<a href=…><span data-cms="…">{label}</span></a>` | `<a href=… data-cms="…">{label}</a>` |
| Пунктуация снаружи | `«<span data-cms="…">{text}</span>»` | `<blockquote data-cms="…">«{text}»</blockquote>` |
| Никакой дочерней разметки внутри | `<span data-cms="…">{v}</span>` | `<div data-cms="…"><svg/>{v}</div>` |
| Одно поле — один элемент | два `<span>` с двумя атрибутами | склейка двух полей в один атрибут |
| Нетекстовые поля — без `data-cms` | иконка/булев флаг правятся формой | `data-cms` на `<svg>` (сотрёт векторный путь) |
| Поле-картинка — через атрибут | `data-cms="…:image" data-fd-attr="src"` на `<ContentImage>` | `data-cms` без `data-fd-attr` |
| Повтор одного поля на странице — норма | телефон в шапке, футере и на карте | попытка «оставить только первое вхождение» |

Синглтон адресуется двумя двоеточиями подряд: `data-cms="sections::cta.title"`.

### 5.5. Переиспользуемые компоненты — `cmsScope`

Если компонент показывается больше чем на одном экране данных, захардкоженный
`data-cms` внутри него будет указывать не туда. Это **тихая порча данных**:
разметка валидна, тест зелёный, а клик на `/about/` правит текст главной.

Решение — проп `cmsScope`:

```astro
interface Props { …; cmsScope?: string }
const { …, cmsScope = 'sections::intro' } = Astro.props;
<h2 data-cms={`${cmsScope}.title`}>{title}</h2>
```

```astro
<IntroSection … cmsScope="pages::about.intro" />
```

Готовые образцы: `IntroSection.astro`, `FeaturesSection.astro` + вызовы из
`index.astro` (дефолт) и `about.astro` (переопределение).

`cmsScope` реализован **во всех секциях шаблона с заголовками** (см. каталог
§9) и в `PageHero` — там он необязательный: без него компонент не печатает
`data-cms` вовсе, что и нужно для страниц со структурным, не редактируемым
заголовком. Новый компонент с заголовком заводите сразу с `cmsScope`.

Две границы механизма (подробно — [`CMS-BUILDING.md`](CMS-BUILDING.md) → «Шаг 5»):
`cmsScope` скоупит только **заголовочные** тексты, а карточки внутри секции
остаются привязанными к своей коллекции; компонент с плоскими полями в
собственном синглтоне (`HeroSection`) скоупу не поддаётся — второму «первому
экрану» нужен свой блок данных.

### 5.6. Шаг 6 — рот-гвард

`scripts/__tests__/annotations.test.ts` читает собранный `dist/*.html` и три
карты:

- `VISUAL_FIELDS` — коллекции-массивы (проверяются на `dist/index.html`);
- `SINGLETON_FIELDS` — синглтоны, видимые на главной или на каждой странице;
- `ROUTE_SINGLETON_FIELDS` — поля, видимые только на конкретном маршруте;
  ключ — путь `dist/<page>/index.html`.

**Новая страница с CMS-полями обязана появиться в `ROUTE_SINGLETON_FIELDS`** —
иначе тест её просто не смотрит и рефакторинг снесёт разметку молча.

## 6. Фаза 5 — картинки

Полная справка — [`docs/IMAGES.md`](IMAGES.md). Минимум, который нужен здесь:

**Два дома, выбор уже сделан:**

- `src/assets/**` — всё контентное. Astro ресайзит, конвертирует в webp, делает
  `srcset`, проставляет `width`/`height`, кладёт с хешем (вечный кэш).
- `public/**` — только то, чему нужен стабильный URL: OG-картинки, favicon,
  шрифты, `robots.txt`, `site.webmanifest`, `fd-edit.js`, `placeholder.svg`.

**Рендер — всегда `<ContentImage>`**, никогда голый `<img>`:

```astro
<ContentImage
  src={item.image}                        {/* ключ реестра, публичный путь или ImageMetadata */}
  alt={item.title}
  widths={[640, 1024, 1600]}
  sizes="(min-width: 768px) 90vw, 100vw"  {/* обязательно, если есть widths */}
  loading="lazy"                          {/* eager+fetchpriority="high" — ровно один LCP на страницу */}
  class="h-full w-full object-cover"
/>
```

**Значение поля-картинки в контенте** — ровно два вида: ключ реестра без
ведущего слэша (`cms/x.png`, `gallery/01.webp`) → оптимизируется; путь со
слэшем (`/images/placeholder.svg`) → отдаётся из `public/` как есть.

**Поле-картинка в схеме** объявляется с `.meta({ format: 'image' })` — это
кладёт `"format": "image"` в контракт и включает загрузчик файла в портале:

```ts
image: z.string().min(1).max(MAX.path)
  .describe('Картинка слайда (загрузите файл)')
  .meta({ format: 'image' }),
```

⚠️ **Любой новый `format` в `.meta()` обязан получить парный
`ajv.addFormat(...)` на стороне портала** (`client-portal/src/services/content-service.ts`).
Без этого портал не скомпилирует схему, и публикация сломается для **всех**
коллекций клиента, а не только для новой. Штампует `format` не только явный
`.meta()` — Zod-нативные типы кладут его сами: `z.iso.date()` →
`"format": "date"`, `z.email()` → `"format": "email"`, `z.url()` →
`"format": "uri"`. В волне блога `z.iso.date()` уронил компиляцию ajv
именно так, без единого `.meta()` в диффе — при добавлении такого поля
парный `addFormat` ищи по типу поля, не по грепу `.meta(`.

Разметка кликабельной картинки — атрибут, не текст:

```astro
<ContentImage src={item.image} alt={item.title}
  data-cms={`showcase:${item.id}:image`} data-fd-attr="src" />
```

Куда клиент грузит файлы — объявлено в контракте: `uploads: { dir:
'src/assets/cms', valuePrefix: 'cms/' }`. Папку `src/assets/cms/` руками не
трогаем.

**Галерея** `/gallery/` собирается из `src/assets/gallery/` автоматически
(«положил файл → появился на странице»), сортировка человеко-числовая — имена
удобно нумеровать `01-…`, `02-…`. Через портал состав галереи сегодня **не
редактируется** — если клиенту это нужно, заводите коллекцию-массив с полем
`image` по образцу `showcase`.

Обслуживание:

```bash
node scripts/optimize-images.mjs --dry   # план пережатия (никогда не трогает src/assets/cms)
npm run assets:orphans                   # что в src/assets/cms уже не используется контентом
```

## 10. Антипаттерны

Собрано из `CMS-BUILDING.md`, `GUIDE.md` и боевых проектов. Каждый пункт —
реально случившийся баг.

**CMS**
1. `data-cms` прямо на `<a>` — правка стирает разметку ссылки.
2. Кавычки/пунктуация внутри аннотированного элемента — уезжают в сохранённое значение и задваиваются.
3. Забыт шаг 4 (регистрация в `COLLECTIONS`) — коллекция работает на сайте, но невидима клиенту.
4. Забыта регенерация `content.schema.json` — ловится тестом, но ловите сами раньше.
5. Захардкоженный `data-cms` в компоненте, который используется на двух страницах — тихая порча данных, ни один тест не поймает.
6. Смена существующего `id`/`singletonKey` — рвёт уже сохранённые правки клиента.
7. Дублирование строки и в JSON, и как хардкод-дефолт в `.astro` — расходятся при первой же правке.
8. Вынос в CMS поля, которое питает JSON-LD или `href`/`tel:`.
9. Забыт `npx astro sync` после правки `content.config.ts` — сборка падает на `keyof DataEntryMap`.

**Вёрстка и производительность**
10. Хардкод hex вместо токена — ребрендинг превращается в обход всех файлов.
11. React-остров там, где хватило бы 0-JS Astro.
12. Больше одного `loading="eager"` на страницу — мобильный LCP расплывается.
13. Тяжёлые несжатые картинки; `<img>` мимо `ContentImage`.
14. Хотлинк Google Fonts вместо self-hosted WOFF2.
15. Внутренние ссылки без завершающего слэша при `trailingSlash: 'always'`.
16. Пробел между инлайн-элементами: при `compressHTML: 'jsx'` пробел **между** тегами схлопывается — разделяйте `flex`+`gap`, а не пробелом в разметке.

**Техника SEO**
17. Расхождение `SITE_URL` и `SITE.url` — битые canonical и sitemap.
18. Один и тот же title/description на всех страницах.
19. Правовые страницы не сверены с кодом: документ описывает не тот состав
    данных, что сайт реально собирает ([LEGAL](LEGAL.md) §3).

Ошибки **содержания** (сток-фото, выдуманные отзывы, заголовок про себя вместо
выгоды) — [`GUIDE.md` §B4](GUIDE.md). Ещё грабли (View Transitions, iOS Safari,
CSS-раскладка, деплой) — [`recipes/gotchas.md`](recipes/gotchas.md).

### Новый синглтон-блок

Отличия от массива: файл — объект `{ "main": { … } }`, в контракте
`kind: 'singleton'` + `singletonKey: 'main'`, чтение `getEntry('<name>', 'main')`,
атрибут с двумя двоеточиями `data-cms="<name>::field.path"`, в тесте —
`SINGLETON_FIELDS` (если видно на главной/каждой странице) или
`ROUTE_SINGLETON_FIELDS` (если только на своём маршруте).

### Новая страница

```astro
---
// src/pages/services.astro
import BaseLayout from '../layouts/BaseLayout.astro';
import Breadcrumbs from '../components/seo/Breadcrumbs.astro';

const seo = SEO.services;                       // ← завести запись в config/seo.ts
const crumbs = [{ name: 'Главная', url: '/' }, { name: 'Услуги' }];
const PAGE = (await getEntry('pages', 'main'))!.data.services;   // ← завести блок в pagesSchema
---
<BaseLayout title={seo.title} description={seo.description} ogImage={seo.ogImage}>
  <main>
    <section class="section pb-0">
      <div class="container-page max-w-3xl">
        <Breadcrumbs items={crumbs} class="mb-6" />
        <h1 class="text-4xl font-bold md:text-5xl" data-cms="pages::services.heading.title">{PAGE.heading.title}</h1>

    <CTASection />
  </main>
```
