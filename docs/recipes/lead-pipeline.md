# Лид-пайплайн v2: форма → черновик → боты (TG + MAX) → Метрика

> Выведено из боевого пайплайна клиентского проекта (2026-08).

Модуль превращает сайт из «формы, которая шлёт письмо» в конвейер лидов:
телефон фиксируется на первом же шаге, брошенные заявки дожимаются
авто-отправкой, менеджер квалифицирует лид кнопками в мессенджере, а
квалификация уезжает в Метрику server-side целями — реклама обучается на
реальных продажах, а не на кликах.

## 1. Архитектура v2

```
Шаг 1 (телефон+согласие) ──«Далее»──▶ POST /api/lead/draft/
        │ цель lead_contact             черновик в DATA_DIR/drafts/ + due_at
        ▼                               (= now + LEAD_FLUSH_MINUTES, дефолт 15)
Шаг 2 (детали, вложения) ─«Отправить»▶ POST /api/lead/complete/
        │ цель lead_submit              merge с черновиком, файлы,
        ▼                               notify ботам (stage=complete)
   [не дошёл до «Отправить»] ──15 мин──▶ флашер: notify (stage=flushed)
                                          server-side цель lead_flushed (MP)
Одношаговая форма ──«Отправить»──▶ POST /api/lead/complete/ (без draft)
```

Участники:

- **Клиент (браузер)** — движок `src/lib/lead-form.ts`: маска +7, валидация,
  UTM/client_id, генерация `lead_id` (идемпотентность и дедуп двойного клика).
- **Роуты Astro** (hybrid, node-адаптер): `POST /api/lead/draft/` — upsert
  черновика, `POST /api/lead/complete/` — JSON или multipart (если файлы),
  merge с черновиком, запись в журнал, fan-out ботам. Ответ обоих —
  `201 {ok, lead_id}`.
- **Флашер** `server/lead-flusher.mjs` — живёт в том же node-процессе
  (run-команда `node --import ./server/lead-flusher.mjs dist/server/entry.mjs`),
  тикает каждые 60 с: черновики с `due_at <= now` уходят ботам со
  `stage=flushed` («клиент оставил телефон, но не заполнил детали» — тёплый
  лид), файл переезжает в `drafts/sent/`. Боты недоступны — повтор на
  следующем тике, после 5 циклов `drafts/failed/` (лид всё равно в журнале).
  Рестарт процесса переживается: на старте флашер пересканирует `drafts/`.
- **Боты TG и MAX** (python-воркеры, `bots/telegram` и `bots/max`) —
  HTTP-приёмники `POST /notify` на `127.0.0.1` (только loopback), порты —
  своя пара на проект, дефолт `8091`/`8092`; auth по заголовку
  `X-Bot-Secret`. Мгновенный ack, доставка в
  фоне с ретраями (5 попыток, backoff 2/4/8/16 с); что не ушло — ложится в
  очередь на диске и повторяется фоном (§5.1). Постят карточку лида с
  кнопками квалификации **✅ Квал / 🔝 Целевой / ❌ Отказ** и показывают друг
  другу нажатый статус.

Принципы (унаследованы от v1 и обязательны):

- **Persist обязателен, notify — нет.** Лид сначала пишется в JSONL, отправка
  ботам — fire-and-forget: лежат оба мессенджера — лид всё равно сохранён,
  клиент видит /thanks/.
- **Honeypot возвращает фейковый 201** — бот не узнаёт, что его поймали,
  а пойманное кладётся в карантин, а не удаляется (см. §5).
- **Доставка не теряется ни на одном участке.** Persist — до notify, а сам
  notify подпёрт двумя очередями (см. §5.1). Заявка — это деньги клиента,
  единственный допустимый исход отказа — «пришла позже», а не «не пришла».
- Повторный `complete` по уже отправленному `lead_id`: ничего нового → 201
  без действий (дедуп); есть новые данные (клиент дожал «Отправить» после
  авто-флаша) → merge + notify `stage=updated` — TG-бот редактирует старую
  карточку до полной и шлёт реплай «клиент дополнил», MAX присылает карточку
  «Дополнение к заявке».

### Кнопки квалификации → Метрика

| Кнопка | Цель |
| --- | --- |
| ✅ Квал | `lead_qualified` |
| 🔝 Целевой | `lead_target` |
| ❌ Отказ | `lead_rejected` |

Основной канал — **Offline Conversions API** Метрики (CSV
`ClientId,Target,DateTime`, OAuth-токен со scope `metrika:offline_data`):
окно привязки **21 день**, потому что менеджер квалифицирует через часы и
дни, а события Measurement Protocol позже 12 часов после визита
отбрасываются. Без OAuth-токена — фолбэк на MP (окно 12 часов).
`lead_flushed` всегда идёт через MP: 15 минут после визита гарантированно
в окне, зато мгновенно и без OAuth. `client_id` бот берёт из текста
карточки; дедуп конверсий по (chat, message, goal); после нажатия на
карточке появляется футер «статус · кто · когда», статус можно
перещёлкивать.

### Цели Метрики модуля

Клиентские (JS-события): `lead_contact` (контакт получен — главная ранняя
конверсия; когда именно срабатывает, зависит от режима формы, см. §4),
`lead_submit` (полная заявка), `lead_thankyou` (показ /thanks/).
Серверные (шлют боты): `lead_qualified`, `lead_target`, `lead_rejected`,
`lead_flushed`. Все заводятся в счётчике как «JavaScript-событие» — см.
[metrika-guide.md](metrika-guide.md).

## 2. Два режима стартера

| | static (дефолт) | hybrid |
| --- | --- | --- |
| Сборка | чистая статика | node-адаптер, `/api/lead/*` живые |
| Куда шлёт форма | `PUBLIC_CONTACT_ENDPOINT` (внешний бэкенд) | `/api/lead/complete/` |
| Черновики / флашер / боты | отключены — роуты и флашер спят | весь пайплайн |

Static-режим ничего не требует: форма работает против любого внешнего
эндпоинта, черновиков нет. Hybrid включает встроенный пайплайн целиком.

## 3. Активация hybrid

1. `astro.config.mjs`: node-адаптер (`output` hybrid), у API-роутов
   `prerender = false`.
2. Переименовать заготовки роутов:
   `src/pages/api/lead/draft.ts.example` → `draft.ts`,
   `src/pages/api/lead/complete.ts.example` → `complete.ts`
   (см. шапки файлов).
3. Задать env (таблица в §6), поднять ботов (`bots/README.md`).

## 4. Когда фиксируется контакт: три режима формы

Ранняя фиксация — это запись лида на сервер ДО нажатия кнопки отправки.
Смысл: телефон уже введён, и если посетитель уйдёт, контакт не пропадёт —
флашер отправит его менеджерам через `LEAD_FLUSH_MINUTES`. Цель
`lead_contact` при этом становится настоящей РАННЕЙ конверсией, а не дублем
`lead_submit` (важно для оптимизации рекламы: ранний сигнал частотнее).

| Режим | Когда пишем контакт | Как включить |
|---|---|---|
| **Двухшаговая форма** | на переходе «шаг 1 → шаг 2» | форма сама зовёт `submitLeadDraft(form)` |
| **Одношаговая с ранней фиксацией** | телефон введён полностью **И** стоит галочка согласия | `data-lead-draft` на `<form>` (проп `earlyContact` у `LeadForm.astro`) |
| **Обычная одношаговая** (дефолт) | по нажатию кнопки | ничего не делать |

**Двухшаговая.** Двухшаговость — свойство формы проекта, не движка: на
переходе форма вызывает `submitLeadDraft(form)` из `lead-form.ts` (keepalive,
не блокирует переход; успех → цель `lead_contact`; повтор гасится гвардом
`form.dataset.draftSent`).

**Одношаговая с `data-lead-draft`.** Кнопки «Далее» нет, поэтому то же
условие движок читает прямо из полей: 11 цифр в телефоне И `checked` у
`input[name=consent]`. Дальше — пауза 1.2 с (иначе на сервер уедет номер,
который ещё дописывают, и менеджер позвонит не туда), затем черновик. Уход со
страницы раньше паузы не теряет контакт: `pagehide` и `visibilitychange`
отправляют немедленно, запрос идёт с `keepalive`. Повторный сабмит сшивается
с черновиком по `lead_id` — карточка у менеджера одна.

**Обычная одношаговая.** Один `complete`, черновиков и авто-флашей нет.
`lead_contact` в этом случае стреляет на успешной отправке вместе с
`lead_submit`, чтобы ранняя цель не пропадала совсем.

> **Правовая рамка (РФ).** Раннюю фиксацию включайте ТОЛЬКО по условию
> «телефон + галочка согласия», как это делает движок. Галочка — то самое
> предварительное согласие, которого требует ст. 18 ФЗ «О рекламе», а
> доказывать его наличие обязан тот, кто звонит; сервер сохраняет время, IP,
> страницу и текст согласия. Записывать номер из формы, где галочка не
> поставлена (и тем более снимать маскирование полей в Вебвизоре Метрики,
> чтобы «подсмотреть» контакт), нельзя: это нарушает и условия Метрики, и
> закон — ч. 4.1 ст. 14.3 КоАП, 300 тыс.–1 млн ₽ на юрлицо.

**Где включать.** На главной форме проекта, где потеря контакта дороже всего.
Попапам и коротким CTA — не нужно: писать данные до явного действия посетителя
там неуместно. Требует hybrid-режим: с внешним `PUBLIC_CONTACT_ENDPOINT`
черновиков нет и атрибут ничего не даёт.

**Сколько это ловит.** Немного: галочка и кнопка обычно рядом, и почти все
жмут кнопку сразу. Ловит сорванную сеть, закрытую вкладку и передумавших.
Главная ценность — ранний сигнал для рекламы, а не поток заявок.

## 5. Серверное ядро (оба роута)

- **Honeypot с карантином** — скрытое поле `hp_token`: заполнено → фейковый
  201, заявка НЕ уходит менеджерам, но и НЕ удаляется: ложится в
  `data/quarantine/<lead_id>.json` и живёт `LEAD_QUARANTINE_TTL_DAYS` (14).
  Удалять нельзя: 21.08.2026 в боевом проекте автозаполнение браузера
  заполнило поле-ловушку у живых людей, и их заявки исчезли бесследно.
  Карантин делает ложное срабатывание заметным (счётчик в `/api/health`) и
  обратимым — номер можно достать и перезвонить. Имя поля тоже важно:
  «company»/«Компания» браузер заполняет охотно, `hp_token` — нет.
- **Не браузер (`looksAutomated`)** — фейковый 201 + карантин
  `reason: not_browser`. Улика: не пришло НИ `Origin`, НИ `Sec-Fetch-Site`.
  Оба заголовка браузер проставляет сам (forbidden headers, из JS не
  переопределить), поэтому живой посетитель шлёт хотя бы один, а автомат —
  ни одного. Разбор боевых POST в `/api/lead/*` (лог Caddy,
  creative-solution.ru, неделя до 29.08.2026): 21 живая заявка с обоими
  заголовками, 1 живая с `Origin` без `Sec-Fetch-*` (Safari до 16.4), 4 бота
  без обоих — правило ловит 4 бота из 4 и не задевает ни одного человека.
  **Почему не по Content-Type:** первая версия проверки искала «JSON без
  Origin» — и спам 28.08.2026 пропустила бы, потому что он пришёл
  `application/x-www-form-urlencoded`. Бот скачал HTML, разобрал форму и
  отправил её поля напрямую: скрытые зеркала (`page_url`, `client_id`,
  `utm_*`) приехали ПУСТЫМИ строками (их заполняет `lead-form.ts`, который у
  бота не выполнялся), а `hp_token` он оставил пустым — ловушка честно
  промолчала. Отличать такое по телу запроса нельзя, только по заголовкам.

> Фильтра по СОДЕРЖИМОМУ полей в пайплайне НЕТ и не должно быть без веской
> причины (решение 29.08.2026): поле свободного текста само просит ссылку на
> текущий сайт, стоп-слова и счётчики ссылок рискуют молча съесть живую
> заявку, а цена ошибки несимметрична — пропущенный спам менеджер удалит сам,
> потерянный лид не заметит никто. Признаки выше смотрят только на то, КАК
> пришёл запрос.

- **Rate limit** — in-memory, 10 запросов / 60 с / IP → 429 (движок формы
  показывает «попробуйте через минуту»).
- **Origin-allowlist** — строится от `SITE.url` (`src/config/site.ts`);
  чужой Origin → 403.
- **Журнал** — append-only `data/leads.jsonl` (все события: draft, complete,
  flush), запись ДО notify.
- **Вложения** — до 5 файлов по ≤5 МБ, тип любой (.heic с айфона, .docx,
  .zip менеджеру нужны не меньше jpg; сайт файлы не открывает и не отдаёт
  по HTTP). Имя на диске строит сервер, из клиентского берётся только
  расширение `[A-Za-z0-9]{1,12}`. Хранятся в `data/attachments/<lead_id>/`.
- **TTL вложений** — по умолчанию бессрочно (файл уже доставлен в переписку
  мессенджера); `LEAD_ATTACH_TTL_DAYS=N` включает автоуборку папок старше
  N дней тем же тиком флашера (PII-гигиена). Текст лида в `leads.jsonl` не
  удаляется никогда.

Файловое хранилище вместо БД — сознательно: объёмы малого бизнеса
(< 100 лидов/день), ноль зависимостей, атомарность через rename.

## 5.1. Надёжность доставки: две очереди и синхронизация ботов

Разбор боевого инцидента 22.08.2026: заявка пришла в MAX и НЕ пришла в
Telegram. Причина — сеть до `api.telegram.org` отвалилась, бот сжёг 5 попыток
за две минуты, написал в лог «попытки исчерпаны» и забыл заявку навсегда.
Спасло только то, что каналов было два.

Отсюда правило: **fire-and-forget допустим только там, где за отказом стоит
очередь.** Участков три, и на каждом свой механизм.

```
браузер ──POST /api/lead/*──▶ роут/флашер ──POST /notify──▶ бот ──sendMessage──▶ чат
      │  сеть моргнула / 5xx        │  не принял (бот лежит)   │  не отправилось (сеть)
      ▼                             ▼                          ▼
 повтор в самом запросе        notify-retry/<адрес>/      DATA_DIR/outbox/<бот>/
 (0.7с, 1.8с — postWithRetry)  повтор раз в минуту        повтор раз в 5 минут
```

**Участок «браузер → сайт» — `postWithRetry` в `lead-form.ts`.** Очереди на
клиенте быть не может (вкладку закроют), поэтому повтор живёт внутри самого
запроса: до трёх попыток с паузами 0.7 и 1.8 с. Дубля это не создаёт —
`lead_id` формы стабилен, и сервер сшивает повтор с уже записанной заявкой по
нему. 4xx не повторяются: 422 повтор не вылечит, а 429 только усугубит.
Дольше ~2.5 с держать посетителя перед кнопкой «Отправка…» нельзя, поэтому
дальше показывается ошибка — и вот тут страхует ранняя фиксация контакта
(§4): если черновик успел уйти, номер уже на сервере.

**Очередь сайта — `data/notify-retry/<slug адреса>/<lead_id>.json`.** Закрывает
случай «бот заявку вообще не получил»: его собственная очередь тут бесполезна,
она хранит уже принятое. Разбор по адресам обязателен: упасть может любой один
бот, и повторять нужно ТОЛЬКО ему — иначе поднявшийся получит карточку второй
раз. Досылает флашер раз в минуту; через `LEAD_NOTIFY_GIVE_UP_HOURS` (24) файл
помечается `.stale` и остаётся для ручного разбора.

Тонкость, которая ломается при беглой правке: когда лежат **оба** бота,
очередь не заводится — черновик и так повторяет отправку сам. Иначе за одну
заявку отвечали бы двое, и карточка задвоилась бы.

**Очередь бота — `DATA_DIR/outbox/<telegram|max>/<lead_id>.json`.** Закрывает
случай «принял, но не смог отправить». Интервал повтора (300 с) намеренно
больше, чем backoff внутри доставки: если сеть отвалилась, ей нужны минуты, а
не секунды. Через `OUTBOX_GIVE_UP_HOURS` (24) — `.stale`. Файл лежит в
`shared/data`, поэтому переживает и рестарт, и редеплой, и откат релиза.

**Почему это не роскошь.** Freim Deploy на каждом редеплое перезапускает
воркеры по очереди — окно, в котором один бот уже лежит, а второй ещё жив,
случается при КАЖДОМ деплое. Без очереди сайта заявка, пришедшая в эту
секунду, достаётся только одному боту. Это не редкая авария, это штатное
состояние системы несколько раз в неделю.

**Синхронизация статусов.** Одна заявка лежит в обоих чатах. Нажали «Отказ» в
MAX — Telegram отвечает реплаем под своей карточкой: `✅ Квал · Иван · 22.08
11:40 · из MAX`. Иначе второй менеджер перезвонит тому же человеку. Боты
общаются по localhost: `POST /peer-status` с тем же `X-Bot-Secret`.

Три решения, каждое из которых оплачено ошибкой:

1. **Реплай, а не правка текста карточки.** Исходный текст в памяти не
   хранится, собирать его заново — лишняя связность между ботами. Реплай виден
   в той же ветке и не может испортить карточку.
2. **Порт соседа — из ЕГО переменной** (`MAX_NOTIFY_PORT` в Telegram-боте и
   наоборот), а не числом в коде. Сменив порт в панели, с зашитым числом вы
   получите тихо неработающую синхронизацию.
3. **Только префиксные имена переменных.** В Freim Deploy общие переменные
   проекта достаются ВСЕМ сервисам: один `PEER_STATUS_URL` на двоих заставил
   бы каждого бота слать статус самому себе. Та же грабля, что с `NOTIFY_PORT`.

Синхронизация — удобство, а не доставка: она без ретраев, и её отказ ничего не
теряет. Очередь — наоборот.

Обе очереди страхуют доставку конкретной заявки; они не заменяют мониторинг
самого пайплайна (упал ли воркер, отвечает ли `/api/health/`) — см.
[monitoring.md](monitoring.md).

## 6. Переменные окружения (сайт)

| Ключ | Значение |
| --- | --- |
| `LEAD_DATA_DIR` | абсолютный путь к данным; локально — `data/` в корне, на сервере — `/srv/<deploy-root>/<project>/shared/data` |
| `LEAD_NOTIFY_URLS` | приёмники ботов через запятую: `http://127.0.0.1:8091/notify,http://127.0.0.1:8092/notify`; пусто → notify выключен |
| `LEAD_NOTIFY_SECRET` | общий секрет (`openssl rand -hex 24`), уходит в `X-Bot-Secret`; тот же секрет — в env ботов |
| `LEAD_FLUSH_MINUTES` | задержка авто-отправки черновика, дефолт `15` |
| `LEAD_ATTACH_TTL_DAYS` | автоуборка вложений; не задан → хранятся бессрочно |
| `LEAD_QUARANTINE_TTL_DAYS` | сколько держать заявки, пойманные ловушкой, дефолт `14`; `0` — не удалять |
| `LEAD_NOTIFY_GIVE_UP_HOURS` | когда прекратить досылать заявку лежащему боту, дефолт `24` (файл → `.stale`) |
| `PUBLIC_CONTACT_ENDPOINT` | static-режим: внешний эндпоинт формы; в hybrid не задавать (оверрайд) |

Эти же ключи читают и боты: **отдельного окружения у ботов нет** — один
файл на весь проект (§6.1). Три ключа сознательно общие на сайт и ботов:
`LEAD_NOTIFY_SECRET` (у ботов раньше звался `NOTIFY_SECRET`),
`LEAD_DATA_DIR` (`DATA_DIR`) и `PUBLIC_YANDEX_METRIKA_ID`
(`METRIKA_COUNTER_ID`). Прежние имена остались фолбэками — установки с
посервисными наборами не ломаются. Остальные ключи ботов (токены, chat_id,
порты, подписи карточки) — см. `bots/README.md`.
Гоча общего env-набора: безпрефиксный `NOTIFY_PORT` получат ОБА бота —
второй не займёт порт и упадёт; порты задавайте префиксованными ключами.
То же и для адреса соседа: `PEER_STATUS_URL` без префикса заставит каждого
бота слать статус самому себе. По умолчанию адрес соседа НЕ нужно задавать
вовсе — бот выводит его из порта соседа (`MAX_NOTIFY_PORT` /
`TELEGRAM_NOTIFY_PORT`), которые и так есть в общем наборе.

| Ключ бота | Значение |
| --- | --- |
| `OUTBOX_RETRY_SECONDS` | период повтора недоставленного, дефолт `300` |
| `OUTBOX_GIVE_UP_HOURS` | когда пометить заявку `.stale`, дефолт `24` |
| `TELEGRAM_PEER_STATUS_URL` / `MAX_PEER_STATUS_URL` | адрес соседа; пусто → выводится из его порта, пустая строка → синхронизация выключена |

## 6.1. Один набор env на три сервиса — и один файл

Окружение у проекта ОДНО. Панель деплоя мержит переменные как **общие ∪
сервисные (сервисные перекрывают по ключу)**, поэтому один набор в «Проект →
Env» доезжает до всех трёх воркеров (`app`, `telegram-bot`, `max-bot`) как
есть. Локально ту же роль играет ОДИН файл — `.env` рядом с сайтом:

- сайт читает его через `node --env-file-if-exists=.env …` (run-команда
  сервиса `app` в манифесте);
- боты находят его сами, поднимаясь вверх от `bot.py`, и первой строкой
  лога печатают, какой файл прочитали. Нестандартная раскладка каталогов →
  `SITE_ENV_FILE=/путь/к/.env`.

В обоих случаях **реальное окружение главнее файла**: и `--env-file`, и
`load_dotenv` не трогают уже заданные значения. Значит на проде набор из
панели побеждает всегда, а забытый на сервере `.env` ничего не перекроет.

Почему не отдельные `.env` у ботов: секрет, каталог данных и номер счётчика
у сайта и ботов обязаны совпадать, а два места для одного значения — это
гарантированное расхождение в тот день, когда одно из них поправят.

⚠️ **Пустое значение — не то же самое, что отсутствующее.** В общем файле
переменная присутствует всегда, поэтому код обязан считать пустую строку
незаданной (`_env()` у ботов, `||` в JS), иначе пустой `MAX_API_BASE=`
затрёт дефолт и бот пойдёт стучаться в никуда. Эта грабля уже поймана.

Вторая ловушка: часть ключей у ботов **обязана различаться** (порт, куда
каждый слушает `/notify`; URL, по которому бот стучится соседу), а общий
набор раздаёт один ключ обоим воркерам одинаково. Решение — **разведение
конфликтных ключей префиксами**:

```dotenv
# ── Общее: сайт и оба бота читают одни и те же ключи ────────────────────────
LEAD_NOTIFY_SECRET=<секрет, openssl rand -hex 24>
LEAD_DATA_DIR=/srv/<deploy-root>/<project>/shared/data
PUBLIC_YANDEX_METRIKA_ID=<ID счётчика>
METRIKA_MP_TOKEN=<токен Measurement Protocol>
METRIKA_OAUTH_TOKEN=<OAuth-токен metrika:offline_data>
BRAND_NAME=<название проекта в карточке>
SITE_HOSTS=<домен сайта>

# ── Telegram-бот ──────────────────────────────────────────────────────────
TELEGRAM_BOT_TOKEN=<токен от @BotFather>
TELEGRAM_GROUP_CHAT_ID=<chat_id группы>
TELEGRAM_NOTIFY_PORT=8091

# ── MAX-бот ───────────────────────────────────────────────────────────────
MAX_TOKEN=<токен из кабинета dev.max.ru>
MAX_CHAT_ID=<chat_id группы MAX>
MAX_NOTIFY_PORT=8092
```

Если вместо префиксов задать общий `NOTIFY_PORT=8091` на оба бота — второй
воркер не займёт порт и упадёт (см. `bots/README.md`). Та же грабля с
`PEER_STATUS_URL`: без префикса каждый бот шлёт статус соседа самому себе.

⚠️ Числа в снипете выше — дефолт для ПЕРВОГО проекта на сервере. Второму
нужна своя пара, иначе он не поднимется вовсе: см. реестр портов ниже.

### Реестр портов ботов (ОДИН на сервер, не на проект)

`8091/8092` — это **дефолт, а не бронь**. Порт слушается на `127.0.0.1`, но
loopback один на всю машину: второй проект на том же сервере получит
`[Errno 98] address already in use`, оба его бота умрут на старте, деплой
свалится и откатится. Так и вышло 27.08.2026 на боевом сервере: новый проект
приехал туда, где уже жил другой, и занятые порты положили весь релиз.
Диагностику это съедает целиком: падают боты, а выглядит как «сломался
деплой сайта».

Заводя проект на общем сервере, выдайте ему свою пару и заведите такую
табличку в доках проекта:

| Проект | telegram | max |
| --- | --- | --- |
| первый | 8091 | 8092 |
| второй | 8093 | 8094 |

Пара задаётся тремя переменными, и все три обязаны совпасть:
`TELEGRAM_NOTIFY_PORT`, `MAX_NOTIFY_PORT` и адреса в `LEAD_NOTIFY_URLS`
(сайт стучится ботам именно по ним). Проверить занятость перед выдачей:
`ss -ltnp | grep 809`.

Оба бота читают своё префиксное имя первым, а безпрефиксное — как фолбэк
для посервисных наборов. Полный список ключей с комментариями — в
`.env.example` сайта; отдельных шаблонов у ботов больше нет.

Первый запуск: вставить набор, оставив `TELEGRAM_GROUP_CHAT_ID` и
`MAX_CHAT_ID` пустыми → force-деплой (смена env сама пересборку не
запускает) → оба бота обязаны подняться даже без токенов и чатов
(`mode=waiting_for_token` в `/health`) → добавить бота в группу, получить
`chat_id` (`/id` для Telegram, лог `bot_added` для MAX) → вписать значение
→ ещё один force-деплой.

## 7. Деплой: мультисервисный frostdeploy.json

Три сервиса в одном репозитории (раскладка стартера: корень репо = сайт,
боты в `bots/telegram` и `bots/max`):

```json

  "services": [
    {
      "name": "app",
      "runtime": "node",
      "role": "web",
      "rootDir": ".",
      "build": { "command": "npm run build", "output": "dist", "install": "auto" },

        "healthcheckPath": "/"

    },
    {
      "name": "telegram-bot",
      "runtime": "python",
      "role": "worker",
      "rootDir": "bots/telegram",
      "build": { "install": "auto" },

      "pythonVersion": "3.12",
```

Заметки:

- Порты 8091/8092 фиксированы в env и слушают только `127.0.0.1` — наружу

- MAX-бот обязан подниматься **без токена** (спит, `/health` отвечает

  релиза.
- Смена env в панели сама пересборку не запускает — нужен коммит или
  force-деплой.
- После деплоя сайта боты не перезапускаются автоматически — это отдельные
  сервисы со своим жизненным циклом.

## 8. PII

- `data/` обязана быть в `.gitignore` — это персональные данные
  (телефоны, имена, файлы клиентов).
- Раскладка `LEAD_DATA_DIR`:
  - `leads.jsonl` — журнал всех событий, хранится бессрочно;
  - `drafts/` (+ `sent/`, `failed/`) — черновики в работе;
  - `attachments/<lead_id>/` — файлы клиентов; TTL —
    `LEAD_ATTACH_TTL_DAYS` (§5).
- Панель деплоя бэкапит только свою БД — бэкап `shared/data` (cron/restic)
  настраивается отдельно ДО первого реального лида.
- Деплой не должен трогать данные: rsync с `--delete` — только внутри
  `dist/`.
- Ссылки согласия в форме ведут на реальную политику обработки ПД (152-ФЗ).

## 9. Лёгкая альтернатива: contact.ts.example (v1)

Для маленького проекта (одна форма, лидов мало, статусы не нужны) пайплайн
v2 — перебор. В стартере остаётся `src/pages/api/contact.ts.example`: один
роут, прямой sendMessage в Telegram, формат ответа `{success}`. Активация —
в шапке файла. **Не смешивать форматы ответов**: v1 отвечает `{success}`,
v2 — `{ok, lead_id}`; движок формы должен работать против одного из них,
а не обоих сразу.
