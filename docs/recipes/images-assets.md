## LQIP — blur-плейсхолдеры (рецепт, эталон-каталог)

Отдельный рецепт, ортогонален переезду в `src/assets/` — делать поверх
реестра, когда на фото-карточках виден белый мигающий фон. Источник блюра —
`ImageMetadata` из реестра (`asset('gallery/1.webp')`), а не произвольный
путь к файлу на диске, как в примере ниже (он ещё не адаптирован под
реестр — доработать при внедрении).

Карточки на фото «мигают белым» до загрузки. Лечится инлайновым
размытым превью ~0.4 KB, сгенерированным НА СБОРКЕ (frontmatter = Node):

```ts
// src/lib/lqip.ts — вызывается из frontmatter
import sharp from 'sharp';
const cache = new Map<string, string>();

export async function lqip(filePath: string): Promise<string> {
  if (cache.has(filePath)) return cache.get(filePath)!;
  try {
    const buf = await sharp(filePath).resize(24).blur(2).webp({ quality: 35 }).toBuffer();
    const uri = `data:image/webp;base64,${buf.toString('base64')}`;
    cache.set(filePath, uri);
    return uri;
  } catch { return ''; }   // не ломать сборку из-за одного файла
}
```
Использование: `style={`background-image:url(${await lqip(...)}); background-size:cover`}`
на контейнере, `<img>` поверх проявляется по загрузке.

## Оптимизация (в стартере: `scripts/optimize-images.mjs`)

```bash
node scripts/optimize-images.mjs --dry   # что будет сделано
node scripts/optimize-images.mjs         # public/images → webp q82 ≤2000px
                                         # src/assets    → webp q82 ≤2000px (кроме cms/)
                                         # public/og     → jpg 1200×630
```
Скрипт обходит три цели (`IMAGES_DIR`/`ASSETS_DIR`/`OG_DIR` в самом файле):
`public/images` и `src/assets` пережимает в webp тем же пайплайном (в
`src/assets` это не замена оптимизации `astro:assets` на сборке, а экономия
веса репозитория и времени сборки самого оригинала), `public/og` —
отдельным пайплайном в jpg 1200×630. `src/assets/cms/**` — единственное
явное исключение (`SKIP_DIRS`): имя файла там — часть значения
(`cms/<uuid>.png`), которое портал уже записал в JSON-контент; смена
расширения при конвертации в webp порвала бы эту ссылку, а `astro:assets` и
так оптимизирует эти файлы на сборке без переименования.
Безопасность: оригинал удаляется только если новый файл существует, непустой
и меньше; смена путей пишется в `scripts/.image-map.json`. Гоча из эталона-каталога:
файлы с расширением `.webp`, внутри которых PNG (редактор «сохранил как»
без конвертации) — по 5-6 МБ; sharp-метаданные выявляют, скрипт пересобирает.

## Ленивая загрузка: три уровня
1. `loading="lazy"` — всё ниже первого экрана (дефолт `ContentImage`);
2. `loading="eager" fetchpriority="high"` — ровно ОДИН LCP-кандидат (hero, обложка статьи);
3. `data-src` + IntersectionObserver — когда нативной лени **недостаточно**
   (два разных случая, см. ниже) — см. также [gotchas.md](gotchas.md).

### Когда `loading="lazy"` не спасает

Уровень 3 нужен не только на iOS. Два независимых случая:

**а) iOS игнорирует lazy под transform-предком** — карусели, marquee.
Картинки не загрузятся никогда (gotchas §6).

**б) Гонка с раскладкой — бьёт во всех браузерах.** Браузер решает, грузить
ли ленивую картинку, по расстоянию до вьюпорта **в момент раскладки**. Пока
картинки выше по странице не загрузились, документ короче реального, и
секция, которая в финале лежит на 3500 px ниже сгиба, в момент решения
оказывается в пороге — браузер её тянет. Замер на реальном лендинге
(боевой проект, прод-сборка, 1440×900): **18 из 33** ленивых картинок ниже двух
экранов ушли в сеть при `scrollY = 0`.

Пока это фоновые фото — не страшно (низкий приоритет, после LCP). Но если
ниже сгиба лежит тяжёлая секция (секвенция кадров, галерея, видео-постеры),
`lazy` не является гарантией, и бюджет первой загрузки протекает.

**Детерминированное лечение** — не отдавать браузеру `src` вообще:

```astro
<!-- В разметке реальный src только у того кадра, который обязан быть
     виден без JS (фолбэк для краулера и reduced-motion). -->
<img src={i === last ? src : undefined} data-src={i === last ? undefined : src}
     alt="" loading="lazy" fetchpriority="low" decoding="async" />
```

```js
// Подставляем src, только когда посетитель реально подошёл к секции.
const io = new IntersectionObserver((entries) => {
  if (!entries.some((e) => e.isIntersecting)) return;
  io.disconnect();
  whenPageLoaded(() => {                       // И load, И близость
    root.querySelectorAll('img[data-src]').forEach((img) => {
      img.src = img.dataset.src;
      delete img.dataset.src;
      img.decode?.().catch(() => {});          // прогрев декода, см. ниже
    });
  });
}, { rootMargin: '250% 0px' });                // ~2,5 экрана форы
io.observe(root);
```

Два условия, а не одно: `load` **И** близость. Если оставить «ИЛИ», сработает
`load` (он наступает через сотни миллисекунд) и вся экономия испарится —
ровно эта ошибка стоила 3,6 МБ трафика на первой загрузке.

Проверять замером, а не на глаз: см.
[PERFORMANCE.md §7](../PERFORMANCE.md#7-бюджет-первой-загрузки-проверять-замером).

### Прогрев декода: загружено ≠ готово к показу

`onload` означает «байты пришли», а не «кадр декодирован». Если картинка
появляется резко (смена кадра, кроссфейд), браузер декодирует её прямо в
момент показа — и она мигает пустотой. Лечение: `await img.decode()` заранее,
на подходе к секции. Готовность набора кадров считать по `decode()`, а не по
`onload`:

```js
await Promise.allSettled(imgs.map((im) => im.decode?.() ?? Promise.resolve()));
```

## Нарезка видео в кадры (`scripts/frames-from-video.mjs`)

Секвенция под скролл-сцену (см. [scroll-scenes.md](scroll-scenes.md)):

```bash
node scripts/frames-from-video.mjs assembly.mov src/assets/scene/seq
node scripts/frames-from-video.mjs assembly.mov src/assets/scene/seq --fps 12 --width 1280 --quality 72
```

Что делает: `ffmpeg` режет ролик с заданным fps, `cwebp` пережимает кадры в
webp нужной ширины, на выходе `frame-001.webp …`. Печатает суммарный вес —
это и есть цена секвенции, её надо знать до подключения.

Две конвенции, без которых пайплайн ломается:

- **12 fps — рабочий минимум.** Ниже сборка «дёргается» на скрабе, выше —
  вес растёт без видимой выгоды (глаз на скролле не различает).
- **Кадры уже финального размера — отдаём мимо `astro:assets`.** Прогонять
  184 файла через sharp на каждой сборке незачем: берём `asset(key).src`
  (реестр) и подставляем как есть. Ровный студийный фон webp сжимает почти
  бесплатно: 1280×720 кадр — 12–26 КБ, вся секвенция из 184 кадров ≈ 3,5 МБ.
