# Фотоархив клиента → каталог: медиа-конвейер

Клиент присылает 5–8 ГБ фотографий: папки «по моделям», выгрузку старого
сайта, кучу HEIC россыпью — и всё это надо превратить в аккуратные карточки
товаров. Этот рецепт — выжимка боевого проекта (1204 кадра, 124 товара),
где путь был пройден целиком, со всеми ошибками. Здесь — как пройти его за
часы.

## Модель: три слоя, названные как на странице

| Поле | Где на странице | Что попадает |
|---|---|---|
| `image` | карточка каталога, OG, фиды | ровно одна обложка |
| `slider[]` | верх карточки, листается миниатюрами | предметные фото товара |
| `gallery[]` | нижняя сворачиваемая секция | интерьеры заказчиков, цех, доставка |

Оба массива опциональны: сайт без нижней секции просто не заполняет
`gallery` — она не рендерится. Слой определяется тем, **что на кадре
главное**, а не где он снят: готовое изделие, снятое в цеху, — это витрина;
цех — это каркас без обивки, поролон и упаковка.

Файлы: `cover.webp` (сгенерированная обложка) / `st-NN.webp` (слайдер) /
`int-NN.webp` (галерея). Слой виден в имени — два скрипта физически не могут
перезаписать друг друга.

## Пять железных принципов (каждый оплачен ошибкой)

1. **Один владелец медиа-полей.** `image`/`slider`/`gallery` пишет ТОЛЬКО
   `apply-media.mjs`. На боевом проекте их писали три скрипта в одну нумерацию
   `NN.webp` — обложками становился пережатый мусор, «кто последний
   отработал, того и кадр».
2. **Решение человека — отдельный файл.** Правки из сортировщика живут в
   `.staging/assignments.json`, а не в `.md`, которые скрипт переписывает.
   Повторный прогон физически не может стереть работу человека. Явный
   `product: null` = «открепить» — тоже решение и тоже старше автоматики.
3. **Ничего не выкидывается молча.** Брак (`usable:false`, водяной знак,
   отбраковка) понижается в галерею, но остаётся видимым. Первая версия
   исключала кадры целиком — и сортировщик показывал кадры, которых на сайте
   нет; заказчик сообщил об этом как о «пропаже фотографий».
4. **Сортировщик и сайт считают слои одним модулем**
   (`scripts/lib/media-layers.mjs`). Две копии правила разошлись бы, и клиент
   правил бы вслепую: на экране одно, на сайте другое.
5. **Дедуп только по перцептивному хешу.** Архивы клиентов — одни и те же
   снимки, пережатые трижды (телефон → мессенджер → старый сайт). md5 у копий
   разный. dHash-64 на боевом проекте склеил 142 дубля и бесплатно перенёс
   атрибуцию между пулами: папка знала товар, архив — тип кадра.

## Конвейер по шагам

Всё проектное — в одном файле `scripts/media.config.mjs`: пулы, алиасы,
лимиты. Скрипты путей проекта не содержат.

```
1. Заполнить media.config.mjs        пулы: откуда кадры и как узнают товар
2. npm run media:index               индекс всех кадров + pHash (кэшируется)
3. [опц.] разметка shot=studio/interior/workshop/… → .staging/classification.json
4. npm run media:apply               раскладка по товарам и слоям
5. npm run media:sorter              данные для /sortirovka/
6. клиент правит в /sortirovka/  →  присылает assignments.json
7. файл → .staging/assignments.json  →  npm run media:apply  →  npm run media:sorter
8. npm run media:review              контактные листы обложек — проверить глазами
```

Генерация обложек (опционально): `npm run media:covers` выкладывает лучший
кадр каждого товара в `.staging/covers-in/<slug>.webp` + промпт-файл с
дефектами исходника → img2img вне репозитория → результат в
`.staging/covers-out/` → `npm run media:covers-import` (валидирует пропорцию
и размер) → `npm run media:apply`.

## Сортировщик `/sortirovka/`

Внутренний инструмент, едет вместе с сайтом (noindex + вне sitemap). Два
экрана:

- **«Разбор»** — чей это кадр: клиент группирует безымянную россыпь;
- **«Слои»** — где показывать: обложка / слайдер / галерея, перекладка
  кнопками.

Открывается на **готовой раскладке** — клиент правит, а не строит с нуля.
Выгрузка содержит только изменённое. Работа сохраняется в localStorage;
«Загрузить файл» позволяет посмотреть чужую выгрузку до применения. После
применения его правок пересоберите данные (`npm run media:sorter`) и
попросите клиента нажать «Сбросить всё».

Шаблон инструкции клиенту: `docs/recipes/photo-archive-client-instruction.md`.

## Разметка типов кадра (шаг 3)

Формат `.staging/classification.json`:

```json
{ "version": 1, "items": { "<id кадра>": {
  "category": "sofa", "shot": "studio", "watermark": false,
  "usable": true, "note": "серый угловой диван, светлая гостиная" } } }
```

`shot`: `studio` (предметка, герой — изделие) / `interior` (у заказчика) /
`workshop` (цех: каркас, поролон, упаковка) / `event` / `render` /
`screenshot`. Размечать стоит только кадры, которые могут попасть в слайдер;
как — VLM по контактным листам 3×3 с номерами, НО:

> **Урок:** дешёвая модель (Haiku) ошиблась на 9 листах из 13, в обе стороны:
> предметку на белом фоне звала «рендером», каркас без матраса на складе —
> «студией». Листы обязан просмотреть человек или модель уровня основной.
> Лист, размеченный однородно («сплошь studio»), почти наверняка не смотрели.
> Разметка по файлу-на-лист с механической проверкой покрытия — иначе
> исполнитель «размечает» не глядя.

### Разметка контактными листами (коллажами)

Ручная разметка идёт не по одному кадру, а по листам 3×3 с номером в углу
ячейки — так человек или VLM проходит сотни кадров быстро, а привязка «номер
→ id» остаётся однозначной. Два независимых захода, одна пара инструментов:

| Заход | Откуда кадры | Скрипты |
|---|---|---|
| `archive` | россыпь без привязки к товару (HEIC/MOV ещё не читаются браузером) | `prepare-gallery.mjs` → `build-collages.mjs` |
| `main` | кадры уже в общем индексе (`media-index.json`), которым тип съёмки не достался по группе дублей | `build-media-collages.mjs` |

Оба захода валидирует и сливает в один `.staging/classification.json`
`merge-classification.mjs --set=<archive|main>`.

**Порядок для `archive` (сырая россыпь):**

```
1. В media.config.mjs: заполнить GALLERY_RAW_DIR + GALLERY_EXCLUDED_FOLDERS
   И СРАЗУ добавить в POOLS { name: 'archive', dir: '.staging/gallery/full', attribution: 'none' }
   — папки на диске ещё нет, но build-media-index.mjs просто увидит её пустой
2. node scripts/prepare-gallery.mjs           конвертация HEIC/MOV → .staging/gallery/{full,thumb,video} + manifest.json
3. node scripts/build-collages.mjs            манифест → контактные листы .staging/collages/
4. разметить листы → .staging/classification/NNN.json (файл на коллаж)
5. node scripts/merge-classification.mjs --set=archive
6. node scripts/build-media-index.mjs         теперь увидит содержимое .staging/gallery/full
```

Шаг 1 (пул в POOLS) — не косметика и не опционален: `merge-classification.mjs`
заранее пересчитывает id разметки под путь, который присвоит
`.staging/gallery/full`, будучи POOLS-пулом (`<STAGING-relative>/gallery/full/<id>.webp`
— то же самое, что получит `build-media-index.mjs` при обходе этой папки).
Другой `dir` в POOLS, опечатка в нём или отсутствие записи — и разметка
станет «сиротой»: она есть в файле, но `resolveFrames` её не находит, кадр
снова выглядит неразмеченным. Поэтому `merge-classification.mjs --set=archive`
и `build-media-collages.mjs` сами проверяют регистрацию пула в рантайме и
падают с подсказкой, если её нет или dir не совпадает — на память полагаться
не нужно.

**Порядок для `main` (кадры уже в индексе):**

```
1. node scripts/build-media-index.mjs
2. node scripts/build-media-collages.mjs      сужает выборку (см. ниже) → .staging/media-collages/
3. разметить листы → .staging/media-classification/NNN.json
4. node scripts/merge-classification.mjs --set=main
```

`build-media-collages.mjs` не листает то, что размечать не нужно:
кадры, уже размеченные напрямую или унаследовавшие тип по группе дублей;
кадры уже `SLIDER_MIN_FRAME_WIDTH` px (media.config.mjs) — они физически не
попадут в слайдер; и пулы целиком, максимум ширины которых ниже этого же
порога — если ни один кадр пула не может выиграть, лист ради него не нужен.

Утилиты для проверки состояния разметки набора `archive`: `classify-gallery.mjs
--stats|--detail`. Точечная правка уже готового `classification.json` в обход
файло-на-коллаж валидатора — `add-classifications.mjs`; годится только для
исправления единичной ошибки в уже проверенных данных, не для первичной
разметки (для неё нужна именно механическая проверка покрытия выше).

## Известные грабли

- **Кодировка выгрузки.** JSON из браузера может прийти с битыми русскими
  ключами (`ÐÐµÐ½Ð´Ð¸Ð½Ð³…`). Имена файлов внутри ключей — ASCII и целы:
  восстанавливайте привязку по ним, сверяя с media-index.
- **HEIC**: sharp без libheif его не читает — всё чтение через
  `lib/readable-image.mjs` (sips, только macOS).
- **Кеш dev-сервера**: долгоживущий `astro dev` отдаёт контент-коллекции
  недельной давности. Перезапуск + удаление `.astro/` (см. gotchas).
- **Одинаковые имена, новое содержимое**: `st-01.webp` после перекладки —
  другой кадр; в dev браузер кеширует старый. Жёсткое обновление. В проде
  проблемы нет — хеш содержимого в имени.
- **REPO_ROOT менять нельзя после первого прогона** — от него считаются id
  кадров, на которые ссылаются решения человека.
- **Дубли, назначенные разным товарам,** достаются одному (первому в группе).
  Кнопка «пометить дубликат» — запланированная, но не построенная фича.

## Чего конвейер сознательно не делает

- **Видео** — в схеме только YouTube ID; файлы видео в репозиторий не едут.
- **Автопривязка россыпи к товару** — это единственное, что человек делает
  руками (или VLM с проверкой человеком).
